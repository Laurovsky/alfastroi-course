## Что такое чистая функция

Функция **чистая**, если:

1. Результат зависит **только от аргументов**. Одинаковый вход — всегда одинаковый выход.
2. У неё **нет побочных эффектов**: она не пишет в базу, не делает сетевых запросов, не меняет глобальные переменные и свои аргументы, не читает текущее время.

Определение из Доки — с важной деталью, которую часто упускают: побочный эффект — это не только запись, но и **чтение** чего-то снаружи.

<Doka from="tools/fp" section="Чистые функции и побочные эффекты">

_Чистая функция_ — это функция, которая не вызывает побочных эффектов (side effects), то есть никак не влияет на состояние внешнего мира.

Чистую функцию можно сравнить с понятием функции из математики: это нечто, что преобразует входные данные по заданным правилам.

🧼 Чистые функции всегда при вводе одинаковых аргументов выдают одинаковый результат. По этому свойству легко отличить чистую функцию от нечистой.

Например, `pureFn()` при вводе 10 и 20 всегда будет возвращать 15, значит она чистая:

```js
function pureFn(a, b) {
  return ((a + b) * a) / b
}
```

А `impureFn()` нечистая — она будет возвращать разные значения, потому что использует случайное число:

```js
function impureFn(a, b) {
  return ((a + b) * a) / Math.random()
}
```

[…] функции производят побочные эффекты, потому что обращаются к глобальным объектам `Math` и `Date`. Да, _любое взаимодействие_ с чем-либо «снаружи» функции считается побочным эффектом, даже получение значений.

Дело в том, что мы не знаем, как именно устроены методы `random()` и `now()` в объектах снаружи. Они могут не только возвращать результат, но и менять состояние окружающего мира, например, меняя какую-то переменную.

</Doka>

Проверим этим правилом `formatDisplayName`: она обращается только к своим аргументам и к методам строк и массивов (`toUpperCase`, `filter`, `map`, `join`), которые сами чистые. Ни `Date`, ни `Math.random`, ни сети. Значит — чистая.

## Почему проект любит чистые функции

В архитектурных правилах Альфастрой (CLAUDE.md §2) записано: классы — только для парсера, экспортёра и workflow; **всё остальное — чистые функции и тонкие сервисы**. Причины практические:

- **Тестируются без окружения.** Для `formatDisplayName` не нужна база, сеть и сервер. Тест выполняется за миллисекунды — поэтому таких тестов в проекте сотни.
- **Предсказуемы.** Нет скрытого состояния — нет «у меня работает, а у тебя нет».
- **Переиспользуются.** Одна функция работает на сервере, в браузере и в Web Worker.
- **Безопасно рефакторятся.** Если тесты зелёные, поведение сохранено.

Почему тестировать их проще всего — Дока формулирует одной фразой:

<Doka from="tools/how-to-simplify-tests" section="Чистые функции и слабое зацепление">

Тестировать чистые функции проще остальных. Для теста нам нужны только исходные данные и ожидаемый результат, никакой дополнительной инфраструктуры не требуется.

На чистых функциях удобно описывать бизнес-логику. Это главная часть приложения, и чем проще она написана, тем меньше трения для тестов и тем надёжнее эта часть написана.

</Doka>

## Функциональное ядро, императивная оболочка

Но приложение без эффектов бесполезно: данные надо прочитать из базы и куда-то записать. Как совместить? Дока описывает приём, который в Альфастрой используется повсеместно:

<Doka from="tools/fp" section="Функциональное ядро в императивной оболочке">

Самый простой и нестрогий способ — использовать чистые функции внутри нечистого контекста. Нечистый контекст (он же императивная оболочка) занимается общением со внешним нечистым миром, а функциональное ядро — только преобразованием данных.

На примере обновления данных в базе это может выглядеть так:

- сперва мы запрашиваем и получаем данные из базы, то есть производим побочный эффект;
- затем преобразовываем данные с помощью чистой функции;
- после записываем данные в базу, то есть снова производим побочный эффект.

Получается такой сэндвич: побочный-эффект, чистое преобразование, побочный-эффект […]

Самое главное — соблюдать ограничение, что только _нечистые функции могут вызывать чистые_, и никогда не наоборот.

</Doka>

## Как распознать скрытую нечистоту

| Код внутри функции | Почему это эффект |
|--------------------|-------------------|
| `Date.now()`, `new Date()` | Результат меняется со временем — передайте время аргументом |
| `Math.random()`, `crypto.randomUUID()` | Недетерминированно |
| `items.sort(...)` на аргументе | `sort` меняет исходный массив — скопируйте: `[...items].sort(...)` |
| `localStorage`, `fetch`, `supabase.*` | Ввод-вывод |
| `console.log` | Формально эффект, но безвредный — допускается для отладки |

### Самая коварная нечистота — мутация аргумента

Объекты и массивы в JavaScript передаются **по ссылке**. Функция, которая меняет переданный массив, меняет его и у вызывающего кода:

<Doka from="js/ref-type-vs-value-type" section="Мутации и неизменяемость">

Изменение значений у полей объекта, добавление или удаление их отразится на всех, кто владеет ссылкой на этот объект. Такие операции называют **мутациями**. В современных веб-разработке мутаций стараются избегать, потому что мутирование объектов может приводить к ошибкам, которые очень трудно отследить.

[…] С массивами, кстати, ситуация точно такая же — если изменять содержимое, то изменения отразятся на всех владельцев ссылки. Для копирования массивов, кроме оператора троеточия, можно использовать метод массива `slice()`. Методы `map()` и `filter()` — они тоже создают новый массив. Причём некоторые другие методы (например `sort()`, `splice()`) при использовании мутируют исходный массив, потому использовать их стоит с осторожностью.

</Doka>

<Doka from="js/array-sort" section="Как понять">

Метод `sort()` работает так же, как и метод `toSorted()`. Основное отличие в том, что метод `sort()` мутирует (изменяет) исходный массив, а метод `toSorted()` возвращает новый массив с отсортированными элементами.

```js
const nums = [20, 1, -10]
const toSortedNums = nums.toSorted((a, b) => a - b)
console.log(nums)
// [20, 1, -10]
console.log(toSortedNums)
// [-10, 1, 20]
const sortedNums = nums.sort((a, b) => a - b)
console.log(nums)
// [-10, 1, 20]
console.log(sortedNums)
// [-10, 1, 20]
console.log(nums === sortedNums)
// true
```

</Doka>

Последняя строка — ключ: `sort()` возвращает **тот же самый** массив. Поэтому в `buildTree` из следующего урока сортировка `bucket.sort(...)` допустима — `bucket` создан внутри функции и наружу не утекал. А вот `items.sort(...)` на аргументе было бы мутацией чужих данных.

<Callout kind="key">

- Чистая функция: **одинаковые аргументы → одинаковый результат** и никакого взаимодействия с внешним миром — даже чтения (`Date.now()`, `Math.random()`).
- Её тест — это только «вход → ожидаемый выход», без моков и базы.
- Эффекты нужны, но их держат **по краям** («сэндвич»): нечистое может звать чистое, но не наоборот.
- Мутация аргумента — тоже эффект. `sort()` и `splice()` меняют массив на месте; `toSorted()`, `map()`, `filter()`, `[...arr]` — нет.

</Callout>

Реализуйте `formatDisplayName` сами. Не подглядывайте в код выше — пусть ведут тесты.

<Callout kind="warning" title="Упражнения — на JavaScript, код проекта — на TypeScript">

Упражнения выполняются прямо в браузере как обычный JavaScript. Код Альфастрой в уроках — TypeScript, и если переписать его дословно, получится `SyntaxError`. Уберите всё, что относится к типам:

| TypeScript (в уроке) | JavaScript (в упражнении) |
|---|---|
| `function f(lastName: string, middleName?: string \| null): string` | `function f(lastName, middleName)` |
| `n![0]` — «точно не null» (non-null assertion) | `n[0]` |
| `value as number` | `value` |
| `interface User { … }`, `type Role = …` | удалить целиком |

Логика при этом та же: TypeScript только добавляет проверку типов до запуска (урок 1.3).

</Callout>
