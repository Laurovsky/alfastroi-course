## Браузер тоже ходит в базу

Клиент Альфастрой использует Supabase для входа и некоторых чтений. Значит, в браузере есть публичный ключ, и любой пользователь может открыть DevTools и отправить запрос к базе **напрямую**, минуя сервер. Защита должна быть в самой базе.

Самая известная атака на базы данных — SQL-инъекция:

<Doka from="tools/web-security" section="SQL-Injection">

Их суть заключается в доступе к данным атакуемого сервиса или их изменению. Ну или удалению, всякое бывает.

[…]

- Злоумышленники могут найти форму на сайте, данные из которой отправляются в базу;
- Написать SQL-код, который будет извлекать данные из какой-то таблицы;
- Подобрать имя таблицы так, чтобы оно совпадало с именем, используемым в Switter;
- Получить все данные из этой таблицы или удалить их.

К примеру, злоумышленники нашли форму логина. Они знают, что эта форма связана с таблицей пользователей. При логине они могут внедрить, например, такой код: `UNION SELECT * FROM users`.

[…] Экранировать SQL-инъекции на клиенте, пожалуй, бессмысленно. Однако у серверных разработчиков обязательно должны быть инструменты, которые позволят работать с пользовательским вводом безопасно.

</Doka>

Как Альфастрой защищена от классической инъекции? SQL нигде не собирается склейкой строк. Сервер передаёт данные **параметрами**: `supabase.rpc('rename_analysis', { p_name: body.name, … })` или `.eq('id', id)`. Postgres получает текст запроса отдельно от значений, и строка `'; DROP TABLE users; --` в поле «Название» останется просто странным названием анализа. В интеграционных тестах то же самое: `c.query('SELECT … ($1, $2)', [analysisId, WCAT_B])`, а не шаблонная строка.

Но у Supabase есть второй риск, о котором и этот урок: даже без инъекции браузер с публичным ключом может **легально** вызвать таблицу или функцию напрямую. От этого защищают RLS и права на функции.

## Row Level Security (RLS)

RLS — политики на уровне строк: Postgres сам добавляет условие к каждому запросу. Упрощённый пример:

```sql
ALTER TABLE execution_analyses ENABLE ROW LEVEL SECURITY;

CREATE POLICY analyses_select ON execution_analyses
  FOR SELECT TO authenticated
  USING (has_access_to_project(project_id));
```

Пользователь увидит только анализы своих проектов, даже если запросит `SELECT * FROM execution_analyses`. Хелперы (`my_role()`, `has_access_to_project(uuid)`) — функции `STABLE SECURITY DEFINER`, которые используют политики.

<Callout kind="tip" title="Производительность RLS">
`auth.uid()` в политике вычисляется **для каждой строки**. Обёртка `(select auth.uid())` превращает его в initplan — одно вычисление на запрос. Миграция 062b ускорила так девять политик.
</Callout>

## Права на функции: главная грабля проекта

Write-RPC (`update_rate`, `submit_for_approval`…) объявлены `SECURITY DEFINER` — они обходят RLS и проверяют права сами. Если браузер сможет вызвать такую функцию напрямую, он обойдёт сервер: idempotency, rate-limit, логи.

Поэтому каждая write-функция заканчивается так:

<Source path="sql/101_rename_analysis.sql" from="REVOKE EXECUTE" to="GRANT EXECUTE" />

Почему **три** роли, а не одна `PUBLIC`? На этом проекте настроены default privileges: каждая новая функция получает **прямой** грант `EXECUTE` ролям `authenticated` и `anon`. `REVOKE … FROM PUBLIC` снимает только грант через `PUBLIC`, а прямые остаются.

<Callout kind="danger" title="Инциденты, из которых выросло правило">
- **2026-06-16.** Залипшая вкладка браузера флудила `update_rate` ~2700 раз в секунду напрямую в базу — CPU 98%. Ответ: миграция 064, `REVOKE` на всех write-RPC.
- **2026-06-19.** После миграции 066 выяснилось: `REVOKE FROM PUBLIC` не закрыл функции — прямые гранты остались. Плюс `set_work_item_allocations` был открыт браузеру с миграций 060/061. Ответ: миграция 067 и правило «все три роли».
- **Обратная гоча (мигр. 093).** У старых функций, наоборот, `anon` получал доступ через `PUBLIC`, и `REVOKE FROM anon` в одиночку не помогал. Вывод: резать всегда `FROM PUBLIC, authenticated, anon`.
</Callout>

И обязательная проверка после деплоя:

```sql
SELECT has_function_privilege('authenticated', 'rename_analysis(uuid,text,integer,uuid)', 'EXECUTE'); -- false
SELECT has_function_privilege('anon',          'rename_analysis(uuid,text,integer,uuid)', 'EXECUTE'); -- false
```

## Чему учат постмортемы

В `docs/superpowers/specs/` лежат постмортемы — разборы инцидентов. Их структура: что случилось, как заметили, причина, что исправили, **какое правило добавили**, чтобы не повторилось. Многие правила из CLAUDE.md — это сжатые выводы постмортемов. Читать их — самый быстрый способ получить опыт, который команда заработала дорогой ценой.

<Callout kind="key">

- Данные передаются в SQL только **параметрами** — склейка строк открывает дорогу инъекциям.
- Браузер может обратиться к базе напрямую, поэтому защита — в самой базе: **RLS** на строки и **права EXECUTE** на функции.
- Новая write-функция: `REVOKE EXECUTE … FROM PUBLIC, authenticated, anon` + `GRANT … TO service_role`, затем проверка `has_function_privilege`.
- Правила проекта — выжимка из постмортемов: каждое появилось после реального инцидента.

</Callout>
