## Аутентификация и авторизация — разные вещи

- **Аутентификация** — *кто вы?* Проверка, что токен подлинный и принадлежит пользователю.
- **Авторизация** — *что вам можно?* Проверка роли и прав на конкретный объект.

Пользователь входит через Supabase Auth и получает **JWT** — подписанный токен с полем `sub` (id пользователя). Клиент отправляет его в каждом запросе: `Authorization: Bearer <token>`.

## authMiddleware

<Source path="server/src/middleware/auth.ts" from="export async function authMiddleware" mark={['getClaims', 'withTimeout', "from('profiles')", 'req.user =']} />

Что здесь важно:

1. **Подпись проверяется криптографически** (`getClaims`): поддельный токен не пройдёт, даже если в нём написан чужой id.
2. **Роль берётся из базы**, а не из токена. Если администратор сменил роль, это действует сразу, без перевыпуска токенов.
3. **Каждый сетевой вызов — с таймаутом 3 секунды.** Если сервис аутентификации завис, лучше быстро ответить 503, чем держать запрос минуту (урок 3.4).
4. `declare global` расширяет тип `Express.Request` полем `user` — дальше по коду `req.user` типизирован.

## requireRole — фабрика middleware

<Source path="server/src/middleware/auth.ts" from="export function requireRole" />

`requireRole('engineer', 'supervisor')` **возвращает** функцию-middleware. Это замыкание: внутренняя функция «помнит» массив `roles`. Такой приём называется фабрикой функций.

Замыкание — одна из ключевых идей JavaScript. Дока объясняет его через область видимости:

<Doka from="js/closures" section="Кратко">

**Область видимости** — это часть программы, в которой мы можем обратиться к переменной, функции или объекту. […]

Области видимости можно представить как коробки, в которые мы кладём переменные. Переменные, которые лежат в одной коробке, могут общаться друг с другом.

[…] Переменные также могут получить доступ к переменным из коробки, в которую вложена их коробка.

</Doka>

<Doka from="js/closures" section="Замыкание">

Замыкание — это функция вместе со ссылкой на внешнее окружение, в котором она была создана. Замыкание возникает в момент создания функции. Возврат вложенной функции позволяет использовать область видимости родительской функции даже после того, как её выполнение завершилось.

[…] Но что, если мы вернём из функции `outer` функцию `inner`?

```js
function outer() {
  let a = 42

  function inner() {
    console.log(a)
  }

  return inner
}
```

[…]

```js
const accessToInner = outer()

accessToInner()
// 42
```

Теперь в переменной `accessToInner` находится функция `inner`, у которой всё ещё есть доступ к локальной переменной `a` функции `outer`!

</Doka>

Сопоставим с `requireRole` строка в строку:

| Пример из Доки | `requireRole` в Альфастрой |
|----------------|----------------------------|
| `outer()` | `requireRole(...roles)` |
| локальная переменная `a = 42` | параметр `roles = ['engineer', 'supervisor']` |
| вложенная `inner()` | возвращаемая `(req, res, next) => { … }` |
| `const accessToInner = outer()` | `router.post('/analyses', …, requireRole('engineer', 'supervisor'), …)` |
| `accessToInner()` печатает 42 | Express вызывает middleware на **каждом** запросе, и она видит `roles` |

`requireRole(...)` выполняется **один раз** — при старте сервера, когда описывается маршрут. А созданная им функция живёт всё время работы сервера и при каждом запросе обращается к «запомненному» `roles`. Тот же приём использует `requireIdempotency('/api/analyses')`: имя эндпоинта запоминается в замыкании.

## Defense in depth: три рубежа

Одна проверка — одна точка отказа. В Альфастрой права проверяются трижды:

Почему так недоверчиво? Дока формулирует главный принцип веб-безопасности:

<Doka from="tools/web-security" section="Кратко">

Веб-приложения, как и любые другие, можно «взломать». Если в приложении есть место, куда можно ввести текст, загрузить изображение, передать какую-то информацию, злоумышленники могут использовать это место для атаки.

[…] Под _атакой_ мы будем подразумевать любое действие, приносящее вред пользователям: утечка их данных, неправильная работа сервиса, невозможность воспользоваться сервисом — всё это последствия различных атак.

</Doka>

Для сервера «место, куда можно передать информацию» — это **любой HTTP-запрос**. Его не обязательно отправляет ваш интерфейс: это может быть `curl`, скрипт или старая вкладка с устаревшим кодом. Поэтому сервер не доверяет ничему, что пришло от клиента: ни роли (берёт её из базы), ни телу (проверяет Zod), ни версии (сверяет в SQL).

<Callout kind="rule" title="Правило проекта §5">
Backend — единственный authority для workflow. Frontend хранит только состояние интерфейса: прячет и выключает кнопки, но **не валидирует права**. Список разрешённых действий клиент получает от сервера: `GET /api/analyses/:id/allowed-actions`.
</Callout>

<Callout kind="key">

- **Аутентификация** — «кто вы?» (JWT, 401). **Авторизация** — «что вам можно?» (роль, 403).
- Роль читается из базы при каждом запросе, а не из токена.
- `requireRole(...roles)` — **замыкание**: функция, созданная один раз, помнит `roles` при каждом вызове.
- Права проверяются трижды: роут → SQL-функция → права на функции в Postgres. Серверу нельзя доверять ничему из запроса.

</Callout>
