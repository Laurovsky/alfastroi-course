## Два вида состояния

Самая частая ошибка во фронтенд-архитектуре — смешивать **данные сервера** и **состояние интерфейса**.

| | Server state | UI state |
|---|---|---|
| Что это | Список подрядчиков, позиции анализа, расценки | Открыта ли модалка, какая вкладка, что выделено |
| Кто владеет | Сервер; клиент держит **кэш** | Только этот экран |
| Может устареть | Да — другой пользователь изменил | Нет |
| Где хранить | Zustand-стор домена | `useState` / `useReducer` в компоненте |

<Callout kind="rule" title="Правило проекта §12">
Серверные данные — в Zustand; `useState` — только для UI. Сторы живут в `entities/<домен>/model` (например, `entities/contractor/model/contractorsStore.ts`), а изолированный стор редактора выполнения — внутри своего виджета.
</Callout>

## Поток данных: откуда стор и зачем

Zustand — наследник идей Flux/Redux. Дока описывает их так:

<Doka from="tools/architecture-data-flow" section="Однонаправленный поток">

В однонаправленном потоке данных каждая часть программы от другой части может либо получить данные, либо передать. Направление такого потока не меняется.

[…] Во Flux приложение состоит из 3 главных компонентов:

- хранилище данных или стор, store;
- диспетчер, dispatcher;
- представление или вью, view.

Задача стора похожа на задачу модели из MVC — он хранит в себе данные. Изменение данных в сторе влечёт за собой изменение представления, то есть перерисовку пользовательского интерфейса.

⚛️ Отметим, что стор сам по себе не перерисовывает интерфейс, это не его задача. Обычно на изменение данных в сторе реагирует UI-фреймворк, например, React.

[…] Когда пользователи совершают какие-то действия, например, нажимают на кнопки, представление вызывает экшен (action) — объект-команду, который говорит, что произошло.

</Doka>

Zustand упрощает Flux: нет отдельного диспетчера и объектов-экшенов. Действие — это просто функция внутри стора (`fetchContractors`), а изменение данных — вызов `set`. Направление потока при этом то же самое.

## Zustand за одну минуту

Стор — это хук, созданный функцией `create`. Внутри — данные и функции-действия, которые меняют данные через `set`:

<Source path="client/src/entities/contractor/model/contractorsStore.ts" from="export const useContractorsStore" to="fetchContractorRateSets: async" mark={['set({ loading: true })', 'translateError']} />

Обратите внимание на шаблон действия загрузки:

1. `set({ loading: true })` — интерфейс покажет индикатор.
2. Запрос через `apiFetch`.
3. Успех → данные в стор, `error: null`.
4. Ошибка → **не бросаем дальше**, а кладём понятный текст в `store.error` (через `translateError` — перевод технических ошибок на русский).
5. `finally` — снимаем `loading`.

Компонент подписывается на нужные поля селектором:

```tsx
const contractors = useContractorsStore((s) => s.contractors)
const fetchContractors = useContractorsStore((s) => s.fetchContractors)
```

## SWR: сначала кэш, потом свежие данные

**Stale-While-Revalidate** — показать то, что есть в кэше, сразу, а свежие данные загрузить в фоне и подменить. Приоритет отображения в проекте:

```ts
cache.length > 0 ? render(cache) : loading ? 'Загрузка' : 'Пусто'
```

Пользователь не видит спиннер при каждом возвращении на страницу. А чтобы кэш не протухал, данные перечитываются при возвращении во вкладку:

<Source path="client/src/shared/lib/use-refetch-on-focus/useRefetchOnFocus.ts" from="export function useRefetchOnFocus" mark={['visibilitychange', 'minIntervalMs) return']} />

Хук слушает два события: `window.focus` (вернулись из другого приложения) и `visibilitychange` (переключили вкладку, разблокировали телефон). Само событие фокуса в Доке:

<Doka from="js/event-focus" section="Кратко">

Событие `focus` вызывается, когда элемент получает фокус. У этого события нет фазы всплытия.

💡 Похожее событие — `focusin` (вызывается после получения элементом фокуса, всплывает). Противоположное событие — `blur` (потеря фокуса).

</Doka>

Throttle 10 секунд: переключились туда-обратно за секунду — повторного запроса не будет. Это приём из семейства «ограничить частоту вызовов»:

<Doka from="js/throttle" section="Кратко">

[…] `throttle()` — это функция, которая вызывает другую функцию, «пропуская» некоторые вызовы с определённой периодичностью.

</Doka>

В `useRefetchOnFocus` throttle написан вручную в три строки: запомнить время прошлого вызова (`lastRefetchAt`) и выйти, если с тех пор прошло меньше `minIntervalMs`. Сравните с `debounce` из урока про идемпотентность: `debounce` ждёт, пока вызовы **прекратятся**, а `throttle` пропускает лишние вызовы, но **не реже чем раз в период** выполняет функцию.

<Callout kind="danger" title="Грабли: isMutatingRef">
`window.confirm('Удалить?')` уводит фокус из окна, а после закрытия диалога фокус возвращается — `useRefetchOnFocus` стреляет и **перечитывает данные до того, как удаление дошло до сервера**. Удалённая строка «воскресает». Решение из проекта: `isMutatingRef = useRef(false)`, ставить `true` **до** confirm, сбрасывать в `finally`, а в `loadAll` проверять флаг.
</Callout>

## Стабильные селекторы

Zustand перерисовывает компонент, когда селектор вернул **другую ссылку** (сравнение `Object.is`). Ловушка:

```ts
// ❌ новый [] на каждом вызове → компонент перерисовывается бесконечно
const rates = useRatesStore((s) => s.byAnalysis[id] ?? [])

// ✅ одна и та же ссылка
const EMPTY: Rate[] = []
const rates = useRatesStore((s) => s.byAnalysis[id] ?? EMPTY)
```

Для составных выборок (`{ a: s.a, b: s.b }`) — `useShallow`, который сравнивает поля, а не ссылку объекта.

<Callout kind="key">

- **Server state** (данные с сервера) — в Zustand-сторе сущности; **UI state** (открыта ли модалка) — в `useState`.
- Поток однонаправленный: View вызывает действие → действие делает `set` → подписанные компоненты перерисовываются.
- **SWR**: сразу показываем кэш, обновляем в фоне; при возврате во вкладку — перечитываем (с throttle 10 с).
- Селектор должен возвращать **ту же ссылку**, если данные не менялись: пустые значения — модульные константы.

</Callout>
