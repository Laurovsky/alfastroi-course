**Feature-Sliced Design (FSD)** — методология организации фронтенд-кода. Она отвечает на вопрос, который рано или поздно встаёт в каждом проекте: *куда положить этот файл и что ему можно импортировать?*

## Проблема, которую решает FSD

Типичная структура маленького React-проекта — по техническим типам:

```text
src/components/  src/hooks/  src/store/  src/utils/  src/api/
```

На 20 файлах это удобно. На 500 — нет: чтобы понять фичу «импорт ТКП», нужно открыть пять папок, а любой компонент может импортировать любой хук. Связи запутываются, и изменение в одном месте ломает другое. Альфастрой прошёл этот путь: папки `components/`, `store/`, `lib/` — legacy, которое постепенно переносилось в FSD.

## Слои

FSD делит код на **слои** по уровню ответственности. Слой может импортировать **только слои ниже себя**:

  nodes={[

    { title: 'widgets', note: 'крупный самостоятельный блок экрана: analysis-editor, execution-editor' },
    { title: 'features', note: 'законченное действие пользователя: import-analysis-tkp, select-approvers' },
    { title: 'entities', note: 'бизнес-сущность: типы, чтение, стор — catalog, analysis, work-item' },
    { title: 'shared', note: 'инфраструктура без бизнес-знаний: api, lib, ui', tone: 'ok' },
  ]}
/>

Чем ниже слой — тем он стабильнее и тем больше у него потребителей. `shared/api/api.ts` используют сотни файлов, поэтому он не должен знать ни о каком анализе. `widgets/analysis-editor` используется в одном-двух местах и может знать о многом.

| Слой | Ответственность | Пример в Альфастрой |
|------|-----------------|---------------------|
| `app` | Инициализация, providers, маршруты | Подключение темы и роутера |
| `pages` | Композиция страницы и маршрута | Выбор анализа и возврат к списку |
| `widgets` | Композиция моделей, features и панелей экрана | `analysis-editor` |
| `features` | Законченное пользовательское действие | `import-analysis-tkp` |
| `entities` | Типы, чтение и работа с бизнес-сущностью | История анализа, каталог |
| `shared` | Общая инфраструктура без доменного знания | fetch, числовой ввод |

## Слайсы

Внутри `widgets`, `features` и `entities` код делится на **слайсы** — по бизнес-смыслу:

```text
features/
├── import-analysis-tkp/
├── select-approvers/
├── manage-additional-acts/
└── edit-allocations/
```

Слайсы **одного слоя не знают друг о друге**. `edit-allocations` не может импортировать `manage-additional-acts`. Если двум фичам нужно взаимодействовать, их соединяет слой выше — виджет.

## Сегменты

Внутри слайса — **сегменты** по техническому назначению:

| Сегмент | Что внутри |
|---------|------------|
| `ui` | Компоненты и UI-события |
| `model` | Состояние, хуки, эффекты, оркестрация |
| `api` | HTTP-контракты |
| `lib` | Чистые вспомогательные функции |
| `config` | Настройки |

```text
features/import-analysis-tkp/
├── api/      запросы загрузки и подтверждения
├── lib/      чистые преобразования строк
├── model/    useAnalysisTkpImport — состояние импорта
├── ui/       TKPUploader, MatchPreview, DiffPreview
└── index.ts  публичный API
```

<Callout kind="tip" title="Сегменты — по необходимости">
В проекте прямо записано: `ui`, `model`, `api` создаются, **когда появляется ответственность**. Пустые папки «на будущее» не создаются.
</Callout>

## Этот курс — тоже на FSD

Откройте исходники курса: `src/app`, `src/pages/lesson`, `src/widgets/lesson-view`, `src/features/run-exercise`, `src/entities/progress`, `src/shared/lib/mini-test`. Упражнение — фича (`run-exercise`), прогресс — сущность (`progress`), тест-раннер — shared (он ничего не знает о курсе), а урок целиком — виджет, который собирает фичи вместе.
