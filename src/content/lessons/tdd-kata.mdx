**Ката** — короткое упражнение, которое решают много раз, оттачивая технику. Здесь мы вырастим настоящую функцию проекта — калькулятор, встроенный в ячейку таблицы объёмов.

## Задача из жизни

Прораб считает объём на калькуляторе телефона и переписывает результат в ячейку. Это медленно и с ошибками. Хочется вводить прямо в ячейку `12,5*4+3` и получать `53`.

Первая идея — `eval(text)`. **Никогда.** `eval` исполняет любой JavaScript: из ячейки можно украсть токен сессии или отправить запросы от имени пользователя. По сути это та же атака, которую Дока описывает как XSS — внедрение чужого кода через поле ввода:

Веб-приложения, как и любые другие, можно «взломать». Если в приложении есть место, куда можно ввести текст, загрузить изображение, передать какую-то информацию, злоумышленники могут использовать это место для атаки.

[…] _XSS_ — это внедрение вредоносного кода на страницы атакуемого сервиса.

[…] 🛡 Экранировать любой пользовательский ввод!

Каким бы маленьким и незначительным ни казалось поле ввода, всё, что пользователь пишет, следует экранировать.

</Doka>

Ячейка объёма — «маленькое и незначительное поле ввода». А значение из неё ещё и сохраняется в базу и показывается другим пользователям (руководителю, отделу документации). Если бы ячейка исполняла код, атака сработала бы в браузере каждого, кто откроет анализ. Поэтому в проекте написан собственный маленький парсер, который **понимает только числа и четыре оператора**:

## Как устроен парсер

1. **Лексер** разбивает строку на токены: числа и операторы. Регулярка с флагом `y` (sticky) обязана совпасть ровно с текущей позиции — мусор между токенами сразу даёт `null`.
2. **Рекурсивный спуск** учитывает приоритет: `number()` читает число с унарным знаком, `product()` собирает `*` и `/`, внешний цикл — `+` и `-`. Каждый уровень вызывает уровень с более высоким приоритетом.
3. **Защиты**: длина ≤ 256 символов, деление на ноль → `NaN` → `null`, все токены должны быть прочитаны (`index === tokens.length`), результат конечен.
4. **Шум плавающей точки**: `0.1 + 0.2 = 0.30000000000000004`. `toPrecision(15)` прячет его, но только для вычисленных значений — введённое число сохраняет точность.

Защита «результат конечен» сделана через `Number.isFinite`:

<Doka from="js/number-isfinite">

Метод `Number.isFinite()` позволяет проверить, является ли переданное в аргументе число конечным. Конечным числом можно считать любое число, кроме бесконечности и `NaN`. […]

В JavaScript есть так же глобальная функция `isFinite()`, которая работает аналогичным образом, но преобразует переданный аргумент в число.

</Doka>

Почему не глобальный `isFinite`? Он сначала **приводит** аргумент к числу: `isFinite('12')` — `true`, `isFinite(null)` — тоже `true` (`null` превращается в `0`). `Number.isFinite` ничего не приводит: не число — значит `false`. Для валидации нужна именно строгая версия.

И зачем вообще проверять? В JavaScript деление на ноль **не бросает ошибку**: `1 / 0` — это `Infinity`, а `0 / 0` — `NaN`. Без проверки в базу мог бы уйти объём «бесконечность». Поэтому в парсере деление на ноль сразу превращается в `NaN`, а в конце `Number.isFinite(result)` отсекает и `NaN`, и `Infinity`.

## Порядок тестов — это план работы

В TDD тесты выстраиваются от простого к сложному, и каждый следующий заставляет сделать **один** шаг обобщения:

| Тест | Что заставляет сделать |
|------|------------------------|
| `42` → 42 | `Number(text)` |
| `12,5` → 12.5 | замена запятой |
| пробелы → null | `trim()` и проверка на пустоту |
| `2+3` → 5 | токенизация и цикл сложения |
| `2+3*4` → 14 | второй уровень приоритета |
| `-3+5` → 2 | унарный минус в `number()` |
| `2+`, `2+abc`, `1/0` → null | защиты от частичного ввода |
| `0,1+0,2` → 0.3 | нормализация точности |

<Callout kind="warning">
Не пытайтесь сразу написать финальную версию. Ценность каты — в ощущении, как тесты **ведут** дизайн: рекурсивный спуск появляется естественно, когда приходит тест на приоритет.
</Callout>

<Callout kind="key">

- Пользовательский ввод **никогда** не исполняется как код: ни `eval`, ни `new Function`. Нужен парсер, который знает только разрешённую грамматику.
- `1 / 0` в JavaScript — это `Infinity`, а не ошибка. Конечность результата проверяют через `Number.isFinite`, а не через глобальный `isFinite`.
- Порядок тестов в TDD — это план работы: каждый новый тест требует ровно одного шага обобщения.

</Callout>
