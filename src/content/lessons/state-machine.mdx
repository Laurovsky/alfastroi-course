## Статусы — это машина состояний

У анализа три статуса, у пакета выполнения — четыре. Между ними разрешены только определённые переходы, и только определённым ролям. Такую модель называют **конечным автоматом** (state machine): состояния + переходы + условия.

## ApprovalWorkflow

Вся логика «какие действия доступны» сосредоточена в одном классе:

<Source path="server/src/modules/approvals/workflow.ts" from="export class ApprovalWorkflow" to="getAllowedActions(ctx: WorkflowContext)" />

<Source path="server/src/modules/approvals/workflow.ts" from="private analysisActions" />

Два метода — два способа использования:

- `getAllowedActions(ctx)` — для **интерфейса**: эндпоинт `GET /api/analyses/:id/allowed-actions` отдаёт клиенту список кнопок и причин, почему кнопка неактивна (`disabledReason`).
- `assertCanTransition(ctx, action)` — для **записи**: перед выполнением действия сервер проверяет его тем же кодом и бросает `ForbiddenError`.

Одна функция решает и что показать, и что разрешить — поэтому интерфейс и сервер не могут разойтись.

Почему правила переходов собраны в одном месте, а не разбросаны по роутам? Это первый принцип SOLID:

<Doka from="tools/oop" section="Принцип единой ответственности (SRP) — S">

Принцип единой ответственности (Single Responsibility Principle) означает, что у модуля должна быть только одна причина для изменения. Весь код, который меняется по этой причине, должен быть собран в этом модуле.

Проще говоря, принцип предлагает нам проводить границы между модулями так, чтобы изменение в бизнес-логике затрагивало как можно меньше модулей, в идеале — один.

Основной инструмент принципа — объединять те части, которые меняются по одной причине, и разделять те, которые меняются по разным.

</Doka>

«Причина для изменения» у `ApprovalWorkflow` одна — **изменились правила согласования**. И история проекта это подтверждает:

- миграция 065 — «admin согласует наравне с supervisor» → в классе появилась функция `canApprove`;
- миграция 066 — «согласует только назначенный на текущий шаг» → в класс добавилась проверка `isAssignedCurrentStep`.

В обоих случаях менялся один файл, и сразу правильно заработали и кнопки в интерфейсе (через `allowed-actions`), и проверки при записи (через `assertCanTransition`). Будь проверка «а можно ли согласовать?» скопирована в пять роутов, каждое изменение правил превращалось бы в поиск всех копий — и одну обязательно бы пропустили (вспомните историю с `deriveRowType`).

<Callout kind="rule" title="Адресное согласование (миграция 066)">
При отправке инженер выбирает 1–2 руководителей. Создаются строки `approvals` со статусом `pending` (step = 1..N, `assigned_to`). Текущий шаг — `MIN(step)` среди pending. Видит и согласует **только назначенный** на текущий шаг; admin — super-access. Reject возвращает анализ автору и удаляет остальные pending-строки — согласование начинается заново.
</Callout>

## requiredVersion

Каждое разрешённое действие несёт `requiredVersion`. Клиент отправляет её обратно, и переход выполняется с проверкой версии. Если между показом кнопки и нажатием кто-то изменил анализ, пользователь получит 409, а не согласует то, чего не видел.

<Callout kind="key">

- Статусы и разрешённые переходы — **машина состояний**: `draft → pending_approval → approved`, reject возвращает в `draft`.
- Все правила переходов — в одном классе `ApprovalWorkflow` (**SRP**: одна причина для изменения — правила согласования).
- Один и тот же код решает, **что показать** (`getAllowedActions`) и **что разрешить** (`assertCanTransition`).
- Каждое действие несёт `requiredVersion`: нельзя согласовать то, что изменилось после показа кнопки.

</Callout>
