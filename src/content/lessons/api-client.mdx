Все запросы клиента к API проходят через одну функцию — `apiFetch` (`client/src/shared/api/api.ts`). Это хороший пример, как **одна точка входа** позволяет навести порядок во всём приложении: таймауты, токены, ретраи и ошибки описаны один раз.

## Основа: fetch

В основе `apiFetch` — встроенная функция браузера:

<Doka from="js/fetch" section="Кратко">

С помощью глобальной функции `fetch()` можно выполнять HTTP-запросы — как получать, так и отправлять данные. Функция возвращает промис, который резолвится в объект ответа, где находится дополнительная информация (статус ответа, заголовки) и ответ на запрос.

</Doka>

У `fetch` есть особенность, о которую спотыкается почти каждый новичок:

<Doka from="js/fetch" section="Обработка ошибок">

Любой ответ на запрос через `fetch()`, например, HTTP-код 400, 404 или 500, переводит `Promise` в состояние _fulfilled_. Промис перейдёт в состояние _rejected_ только если запрос не случился из-за сбоя сети или что-то помешало выполнению `fetch()`.

[…] Чтобы обработать ошибку запроса, необходимо обращать внимание на поле `ok` в объекте ответа `Response`. В случае ошибки запроса оно будет равно `false`.

```js
fetch('https://jsonplaceholder.typicode.com/there-is-no-such-route')
  .then((response) => {
    // Проверяем успешность запроса и выкидываем ошибку
    if (!response.ok) {
      throw new Error('Error occurred!')
    }

    return response.json()
  })
```

</Doka>

Вот почему в `apiFetch` есть строка `if (!res!.ok) { … }`: без неё ответ 409 «Конфликт версий» выглядел бы для вызывающего кода как успешный, и интерфейс показал бы «Сохранено». `apiFetch` превращает каждый неуспешный статус в исключение — нужного класса.

Сам `apiFetch` написан как `async`-функция:

<Doka from="js/async-await" section="Кратко">

Добавленное перед определением функции ключевое слово `async` делает функцию асинхронной. Возвращаемое значение такой функции автоматически оборачивается в Promise […]

Асинхронные операции выполняются не сразу: код отправил запрос к API и ждёт, пока сервер пришлёт ответ. Ключевое слово `await` используется, чтобы дождаться выполнения асинхронной операции.

</Doka>

## Токен: обновить заранее, не зависнуть

<Source path="client/src/shared/api/api.ts" from="async function getValidToken" mark={['readSessionFromStorage()', 'REFRESH_THRESHOLD_S)']} />

Если токен истекает меньше чем через минуту, он обновляется **до** запроса — не дожидаясь 401. Если `getSession()` завис (а такое бывает), сессия читается напрямую из `localStorage`: лучше отправить запрос со старым токеном, чем не отправить никакого.

Здесь стоит остановиться: Дока предупреждает, что хранить токены в `localStorage` — риск.

<Doka from="tools/browsers-storages" section="Web Storage">

[…] любой скрипт, загруженный на странице, может иметь доступ к Web Storage на этой странице. Поэтому не стоит хранить там приватную информацию или токены авторизации, так как таким скриптом может являться вредное браузерное расширение, которое ворует информацию пользователя.

</Doka>

Почему тогда Альфастрой так делает? Это не решение проекта: `supabase-js` по умолчанию хранит сессию в `localStorage`, и `apiFetch` лишь читает её оттуда как запасной путь. Альтернатива — `httpOnly`-cookie, недоступные JavaScript, — потребовала бы, чтобы вход шёл через собственный сервер. Риск снижают другие меры: короткоживущий access-токен (около часа), отсутствие стороннего JavaScript на страницах, строгая проверка прав на сервере. Это настоящий инженерный компромисс, и полезно видеть его явно.

Ключ идемпотентности нормализуется **до** цикла попыток — поэтому повтор после таймаута идёт с тем же ключом, и сервер вернёт сохранённый ответ (урок 3.3). Повторяются только идемпотентные запросы (урок 3.4).

## 401 и обновление токена

Токен мог истечь, пока вкладка спала. Вместо того чтобы выкинуть пользователя на логин, `apiFetch` один раз обновляет сессию и повторяет запрос:

<Source path="client/src/shared/api/api.ts" from="if (res!.status === 401 && !authRetried)" to="return actualFetch(true);" />

Флаг `authRetried` — защита от бесконечного цикла: если и после обновления 401, ошибка честно уходит наверх. Обновление сессии тоже обёрнуто в 3-секундный таймаут.

<Callout kind="danger" title="Грабли: залипший auth-мьютекс">
`supabase.auth.refreshSession()` на мёртвом сокете может повиснуть, и все последующие `getSession()` встают в очередь за ним — приложение «замерзает» без ошибок. Поэтому правило §14: **3-секундный `withTimeout` на все вызовы `supabase.auth.*`**, плюс запасной путь — прочитать сессию из `localStorage`.
</Callout>

## Ошибки как типы

```ts
if (res.status === 403) throw new ForbiddenError(body.error)
if (res.status === 409) throw new ConflictError(body.error)
throw new ApiHttpError(body.error || `HTTP ${res.status}`, res.status, body.code)
```

Вызывающий код различает ошибки через `instanceof`: `ConflictError` → открыть `ConflictDialog` и перезагрузить, остальное → `translateError` и сообщение. Статус `204 No Content` не парсится как JSON — частая причина «Unexpected end of JSON input».

<Callout kind="info" title="Телеметрия зомби-клиентов">
Ответы 409/429 отправляются в Sentry (не чаще раза в минуту): лавина таких ответов — сигнатура «зомби-вкладки», которая в цикле повторяет запрос. Такие инциденты в проекте уже были, и теперь они видны в мониторинге.
</Callout>

<Callout kind="key">

- Все запросы клиента идут через **один** `apiFetch`: таймаут, токен, ретраи и ошибки описаны в одном месте.
- `fetch` **не** отклоняет промис на 4xx/5xx — нужна проверка `res.ok`. `apiFetch` превращает статус в класс ошибки: 403 → `ForbiddenError`, 409 → `ConflictError`.
- Токен обновляется заранее (меньше 60 с до истечения); на 401 — одно обновление и один повтор.
- Сессия в `localStorage` — компромисс `supabase-js`: удобно, но доступно любому скрипту на странице.

</Callout>
