Баги неизбежны. Отличие зрелого проекта — **один и тот же баг не возвращается**. Инструмент для этого — регрессионный тест.

<Doka from="tools/how-to-test-and-why" section="Уменьшают количество регрессий">

**Регрессия** — это ошибка, которая возникает в уже работающей части системы после изменений в коде. Это может быть добавление новой функциональности в старый код или доработка общих функций.

В нашей голове может уместиться лишь небольшой кусочек системы, которую мы программируем. Большая часть системы всегда находится вне поля нашего зрения. Это значит, что при добавлении функциональности мы можем не учесть особенности работы уже существующего кода.

Тесты закрывают такие ошибки, потому что падают при возникновении неучтённой ситуации и не дают ей отправиться в продакшен.

</Doka>

В Альфастрой это не абстракция. Эвристика `deriveRowType` была скопирована в шесть мест — никто не мог удержать в голове все копии, и одна разошлась с остальными. А тесты «не дают отправиться в продакшен» буквально: CI запускает их на каждом pull request, и деплой из `main` начинается с того же CI.

## Правило: сначала тест, воспроизводящий баг

Когда приходит баг-репорт, порядок такой:

1. Написать тест, который **воспроизводит** баг. Он должен быть красным — это доказательство, что вы поняли причину.
2. Исправить код. Тест становится зелёным.
3. Тест остаётся в проекте навсегда: если кто-то случайно вернёт старое поведение, CI упадёт.

Пример из урока про типы — тест с комментарием о прошлой ошибке:

```ts
// Пробельный код — материал (trim): раньше инлайн-версия ошибочно давала work.
expect(deriveRowType(row({ code: '  ', unit: 'м' }))).toBe('material')
```

<Callout kind="tip">
Комментарий «почему этот тест существует» экономит часы будущему разработчику, который захочет его удалить как «странный».
</Callout>

Регрессионный тест заодно становится документацией: он фиксирует не только «как должно работать», но и «как однажды сломалось».

<Doka from="tools/how-to-test-and-why" section="Автоматическая документация">

Тесты не врут 😃
Они действительно показывают, как работает система.

Дополнительная документация может устареть, особенно часто это случается с комментариями. Если документация устарела, у нас появляется два источника правды: документация и код. Это плохо, потому что непонятно, чему верить, и как программа должна работать. Тесты же точно говорят, как программа работать должна и работает ли.

</Doka>

### Данные для теста: называйте ошибку в имени

Хорошая регрессия читается без пояснений. Дока советует выносить «что не так с данными» прямо в имя переменной:

<Doka from="tools/testing-and-fake-objects" section="Тестовые данные и инфраструктура">

Бывает полезно заранее создать (или сгенерировать) данные для стандартных сущностей типа пользователя, товара, настроек и т. д., а в тестах использовать их копии. Это делает код тестов чище и короче […]

Для данных с намеренными ошибками полезно выносить эти ошибки в названия переменных, чтобы в коде тестов было видно, какие именно данные мы используем:

```js
const fakeUser = {
  name: 'Alex',
  email: 'alex@site.com',
  role: 'user'
}

const fakeUserInvalidEmail = {
  ...fakeUser,
  email: 'упс! неправильная почта'
}
```

</Doka>

В `deriveRowType.test.ts` тот же приём сделан функцией: хелпер `row(o)` подставляет поля по умолчанию, а тест передаёт только то, что важно для случая — `row({ code: '  ', unit: 'м' })`. Сразу видно: дело в коде из пробелов.

## Кейс: дубли строк в ТКП

Реальная проблема, которая не раз ломала импорт. Инженер повторно загружает смету (ТКП), и система должна понять, какие строки **новые**, какие **удалены**, какие **изменились** — чтобы не потерять уже внесённое выполнение.

Наивное решение — сопоставить строки по коду работы через `Map`. Но в реальных ТКП **один код встречается несколько раз**:

| Код | Наименование | Примечание | Объём |
|-----|--------------|------------|-------|
| 6.2.3.1.4 | Монтаж трубопровода | Работы до 5-и метров | 120 |
| 6.2.3.1.4 | Монтаж трубопровода | Работы выше 5-и метров | 40 |

`Map` по коду оставит только последнюю строку — первая молча «исчезнет», а вместе с ней и выполнение. Решение описано в шапке модуля:

Ключевая идея — **multiset с потреблением**: для каждого ключа хранится не одна строка, а очередь. Новая строка забирает (потребляет) первую подходящую существующую — так два дубля спариваются с двумя дублями по порядку.

Почему простой `Map` не справляется — прямо из определения:

<Doka from="js/map" section="Кратко">

`Map` — коллекция для хранения данных любого типа в виде пар `[ключ, значение]`, то есть каждое значение сохраняется по _уникальному_ ключу […]

</Doka>

Ключ уникален, значит на ключ `6.2.3.1.4` помещается **одно** значение: второй `set` с тем же ключом молча перезапишет первый. Решение — хранить по ключу массив-очередь и доставать из неё строки по одной:

<Doka from="js/array-shift">

Метод `shift()` удаляет из массива элемент с индексом 0 и возвращает значение удалённого элемента.

</Doka>

`shift()` делает две вещи сразу: возвращает первую строку очереди **и** удаляет её. Это и есть «потребление»: спаренная существующая строка больше никому не достанется.

Проходы идут каскадом ключей: сначала самый точный (`код + имя + примечание`), затем более грубые — для строк, у которых в новом файле поправили примечание.

<Callout kind="key">

- Регрессия — поломка того, что уже работало. Тесты ловят её до продакшена.
- Баг-фикс начинается с **красного теста**, который воспроизводит баг; после исправления тест остаётся навсегда.
- В тестовых данных ошибка должна быть видна из имени (`fakeUserInvalidEmail`, `row({ code: '  ' })`).
- `Map` хранит одно значение на ключ. Для дублей — очередь на ключ и `shift()`, то есть потребление.

</Callout>
