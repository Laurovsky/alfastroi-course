Весь проект написан на TypeScript. Самые полезные его возможности для бизнес-логики — **типы-объединения** (union types): они описывают конечный набор значений и позволяют компилятору проверить, что вы обработали каждое.

## Зачем вообще TypeScript

<Doka from="tools/static-types" section="Кратко">

В JavaScript **слабая динамическая** типизация. Это означает две вещи:

1. При операции с переменными разных типов они будут автоматически приведены к одному типу.
2. Любая переменная может произвольно менять свой тип во время выполнения программы. […]

Эти свойства языка часто усложняют разработку больших и надёжных приложений. Поэтому появились решения, которые добавляют в JavaScript **строгую статическую** типизацию. «Строгая» означает запрет автоматического приведения типов, «статическая» значит, что проверка типов происходит на этапе сборки приложения или написания кода.

</Doka>

<Doka from="tools/static-types" section="Как понять">

TypeScript — надмножество JavaScript. На практике это означает, что любой JavaScript-код является корректным TypeScript-кодом. А вот обратное неверно.

Главное преимущество строгой статической типизации — возможность найти ряд ошибок ещё на этапе написания кода. […]

```ts
// Аргумент функции всегда должен быть объектом,
// у которого есть строковое поле name
function generateEmail(user: { name: string }) {
  return `${user.name}@mycompany.com`
}

// При вызове функции программист передает другой объект,
// происходит ошибка во время сборки, программист её замечает и исправляет
generateEmail({ fullName: 'Петр Сергеевич Никольский' })
```

Чем раньше обнаруживается ошибка, тем легче её исправить. […] По сути, статическая типизация (как и статический анализ) добавляет в процесс разработки программы ещё один шаг — проверку типов, который выполняется перед сборкой проекта и может помочь найти ошибки на раннем этапе.

[…] Если контекст непонятен языку, он пометит тип переменной как `any`. Это означает, что в ней может лежать значение любого типа.

</Doka>

Про `any` — важное следствие для Альфастрой. Флаг `"strict": true` в `tsconfig` включает, среди прочего, запрет **неявного** `any`: если TypeScript не смог вывести тип параметра, это ошибка, а не тихое «что угодно». Для данных из сети (тип которых заранее неизвестен) правильный выбор — `unknown` плюс проверка через Zod (модуль 3).

<Callout kind="warning" title="Как на самом деле в репозитории">
`CLAUDE.md` декларирует «TypeScript strict», но проверка конфигов показывает: `strict` включён в `server/tsconfig.json`, а в `client/tsconfig.app.json` этого флага **нет**. Явный `any` встречается в обеих частях — около 80 мест, чаще всего при разборе строк Excel (`useRatesImport.ts`) и ответов базы. Это хорошее упражнение после курса: включить `strict` в клиенте и пройтись по ошибкам компилятора. Документация и код расходятся чаще, чем кажется, — проверяйте утверждения по конфигам.
</Callout>

Ещё одно следствие «проверки на этапе сборки»: типы **стираются** при запуске. В браузере и в Node.js выполняется обычный JavaScript, поэтому TypeScript не защищает от неправильных данных, пришедших по сети. Этим занимается валидация.

## Union из строковых литералов

Строка ТКП бывает трёх видов. Вместо `string` проект пишет:

```ts
type RowType = 'section' | 'work' | 'material'
```

Теперь `deriveRowType(row) === 'secton'` — ошибка компиляции (опечатка), а не тихий баг. Так же описаны статусы и роли:

Ключевой метод здесь — `trim()`:

<Doka from="js/string-trim">

Метод `.trim()` удаляет пробельные символы с обеих сторон строки и возвращает новую строку, не изменяя при этом исходную.

[…] Под «пробельными» имеются в виду не только сами пробелы, но и их ближайшие родственники: символы переноса строки `\n` и табуляции `\t`.

</Doka>

Ячейки Excel часто содержат «невидимый мусор»: пробел после кода, перенос строки внутри ячейки. Без `trim()` ячейка `'  '` выглядит пустой для человека, но для `if (row.code)` это непустая строка — значит «работа». Именно этот баг и был в проекте.

Прочтите JSDoc: раньше эта эвристика была скопирована в **шесть мест** в чуть разных вариантах, и одна из копий не делала `trim()`. Строка с кодом из пробелов в одном месте считалась работой, в другом — материалом. Решение — **одна каноническая функция** и тест на ней:

<Callout kind="tip" title="DRY для правил, а не для букв">
Принцип «не повторяйся» важнее всего для **бизнес-правил**: если правило описано дважды, рано или поздно копии разойдутся. Повтор похожего, но независимого кода — меньшее зло.
</Callout>

<Callout kind="key">

- TypeScript проверяет типы **до запуска**; при выполнении их уже нет — данные из сети всё равно валидируются.
- Union из литералов (`'draft' | 'approved'`) превращает опечатки в ошибки компиляции.
- Discriminated union с полем-меткой (`entityType`) позволяет TypeScript **сужать** тип внутри `if`.
- Одно бизнес-правило — одна функция. Копии правила расходятся (история с `trim()`).

</Callout>
