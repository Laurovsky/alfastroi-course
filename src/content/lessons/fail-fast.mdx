## Медленный отказ хуже быстрого

Сетевой вызов может не упасть, а **зависнуть**: TCP-соединение умерло, но клиент об этом не знает. Без таймаута запрос висит минутами, пользователь видит бесконечный спиннер, а на сервере копятся незавершённые запросы.

**Fail-fast** — принцип «падай быстро и понятно». Ошибку через 3 секунды можно показать и повторить. Зависание — нельзя.

## Сначала: что такое промис

Всё в этом уроке построено на промисах. Освежим определение:

<Doka from="js/promise" section="Кратко">

Промис (Promise) — специальный объект JavaScript, который используется для написания и обработки асинхронного кода.

Асинхронные функции возвращают объект `Promise` в качестве значения. Внутри промиса хранится результат вычисления, которое может быть уже выполнено или выполнится в будущем.

Промис может находиться в одном из трёх состояний:

- _pending_ — стартовое состояние, операция стартовала;
- _fulfilled_ — получен результат;
- _rejected_ — ошибка.

Поменять состояние можно только один раз: перейти из `pending` либо в `fulfilled`, либо в `rejected`.

</Doka>

Зависший запрос — это промис, который **навсегда остался в `pending`**. Ни `then`, ни `catch` не сработают никогда, и код, который ждёт результат через `await`, будет ждать вечно. Задача таймаута — принудительно получить `rejected` за разумное время.

## withTimeout: гонка промисов

<Doka from="js/promise-race">

Метод `race()` — это один из статических методов объекта `Promise`. Его используют, чтобы запустить несколько промисов и получить результат того, который выполнится быстрее.

[…] Создадим несколько промисов, где `theFastest` завершается с ошибкой.

```js
const slow = new Promise(
  resolve => setTimeout(() => resolve(1), 6000)
)
const fast = new Promise(
  resolve => setTimeout(() => resolve(2), 3000)
)
const theFastest = new Promise(
  (resolve, reject) => setTimeout(() => reject('Some error'), 1000))
```

Передадим массив из созданных промисов в `Promise.race()`:

```js
Promise.race([slow, fast, theFastest])
  .then((value) => {
    console.log(value)
    // Промис с ошибкой завершился быстрее —
    // эта часть проигнорируется
  })
  .catch((error) => {
    console.log(error)
    // 'Some error'
  })
```

</Doka>

А теперь посмотрите на `withTimeout` из Альфастрой — это пример из Доки, где `theFastest` — таймер с ошибкой, а `slow` — настоящий сетевой запрос:

<Source path="server/src/lib/withTimeout.ts" />

Если запрос успел — побеждает он. Если нет — первым «финиширует» `reject(new TimeoutError(label, ms))`, и мы получаем ошибку с меткой, по которой в логах видно, **какой** вызов завис (`auth.getClaims`, `profiles.select`…).

<Callout kind="warning" title="Деталь для внимательных">
Таймер в этой реализации не очищается после успешного ответа: `setTimeout` всё равно сработает и вызовет `reject` у промиса, который уже никому не нужен. По правилу «состояние меняется только один раз» это безвредно — результат гонки уже определён. Но таймер живёт лишние секунды. Дока рекомендует так не делать:
</Callout>

<Doka from="js/cleartimeout">

`clearTimeout()` очищает таймаут установленный с помощью `setTimeout()`.

[…] Не всегда бывает необходимо, чтобы отложенный вызов обязательно сработал. `clearTimeout()` прерывает таймер и установленная функция уже не вызовется.

[…] Мы рекомендуем всегда подчищать таймеры, если они больше не нужны. Даже если в самой функции стоят необходимые проверки и её вызов не приведёт к неожиданным последствиям.

</Doka>

Где очистить таймер, если гонка может закончиться и успехом, и ошибкой? В `finally`:

<Doka from="js/promise-finally">

Метод `finally()` используют для выполнения кода при завершении промиса. Код выполнится как при переходе промиса в состояние `fulfilled`, так и в `rejected`.

[…] Обычно такой код занимается уборкой после операции — скрывает индикаторы загрузки, закрывает меню и так далее.

</Doka>

В упражнении ниже так и сделайте: `Promise.race([...]).finally(() => clearTimeout(timer))`.

### Таймаут — не отмена

Есть ещё одна тонкость. `Promise.race` перестаёт **ждать** запрос, но не **останавливает** его: соединение остаётся открытым, а ответ, если придёт, будет выброшен. Чтобы действительно прервать `fetch`, нужен `AbortController`:

<Doka from="js/abort-controller">

`AbortController` — это встроенный объект, который позволяет отменять выполнение любых операций. Появился в ES2018 (ES9) для отмены fetch запросов, но позже его применение расширилось на другие операции.

[…] Состоит из:

1. Метода `abort([reason])` для отмены операции […]
2. Свойства `signal` […]

</Doka>

Клиентский `apiFetch` в Альфастрой использует обе техники сразу: гонку с таймером (чтобы вернуть ошибку через 45 секунд) **и** `fetchController.abort(new TimeoutError(...))` в том же таймере (чтобы браузер закрыл соединение). Серверный `withTimeout` проще — он оборачивает вызовы Supabase, которые сами принимают `signal` не везде.

## Правила §14 проекта

| Где | Таймаут | Зачем |
|-----|---------|-------|
| Любой `apiFetch` из браузера | 45 с | глобальная страховка |
| `supabase.auth.*` на клиенте | 3 с | auth-мьютекс Supabase умеет залипать на мёртвом сокете |

## Какой запрос можно повторить

После таймаута соблазнительно повторить запрос. Но мы **не знаем**, дошёл ли первый:

<Source path="client/src/shared/api/api.ts" from="* Безопасно ли авто-ретраить запрос после TimeoutError?" to="hasIdempotencyKey(options.headers);" withDoc={false} />

Почему повтор опасен:

- **PATCH** с `prev_version = 5`: первый запрос успел, версия стала 6. Повтор получит **ложный 409** «изменено другим пользователем» — хотя изменил сам пользователь.
- **DELETE**: первый запрос удалил запись. Повтор получит «не найдено» и **ложную 500**.
- **POST без ключа**: создаст дубль.

Безопасны только GET/HEAD (без побочных эффектов) и запросы с `Idempotency-Key` (сервер вернёт кэш).

<Callout kind="key">

- Зависший запрос — промис, навсегда оставшийся в `pending`. Таймаут переводит его в `rejected` за предсказуемое время.
- `withTimeout` = `Promise.race([запрос, таймер с reject])`. Таймер стоит убирать через `clearTimeout` в `finally`.
- Гонка перестаёт **ждать**, но не **отменяет** запрос; для отмены `fetch` нужен `AbortController`.
- Повторять после таймаута можно только **идемпотентные** запросы: GET/HEAD или запросы с `Idempotency-Key`.

</Callout>
