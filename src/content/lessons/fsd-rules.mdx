Слои и слайсы бесполезны, если правила импорта можно нарушить незаметно. В Альфастрой они проверяются автоматически в CI скриптом `npm run lint:architecture`.

Такой скрипт — это линтер, то есть инструмент статического анализа:

<Doka from="tools/static-analysis" section="Кратко">

Часто можно сказать, насколько код программы корректен, даже не запуская её. Процесс исследования исходного кода без запуска называют __статическим анализом__ или __линтингом__, а программу, которая это делает — __статическим анализатором__ или __линтером__.

</Doka>

<Doka from="tools/static-analysis" section="Как понять">

Линтер — это программа, которая разбирает исходный код на стандартизированные кусочки, а потом даёт эти кусочки на проверку специальным __плагинам__. Плагин получает разобранный участок кода и проверяет его на корректность по ряду правил, которые определены в этом плагине.

</Doka>

`frontend-boundaries.mjs` устроен ровно так: он разбирает каждый файл компилятором TypeScript (`ts.createSourceFile`), достаёт из синтаксического дерева все `import` и `export … from` и прогоняет каждую пару «откуда → куда» через три правила. ESLint проверяет код **внутри** файла, а этот скрипт — **связи между** файлами. Поэтому в CI они идут отдельными шагами.

## Три правила

1. **`fsd-layer`** — нельзя импортировать слой выше своего.
2. **`fsd-slice`** — нельзя импортировать соседний слайс того же слоя.
3. **`fsd-public-api`** — в чужой слайс можно войти только через его `index.ts`.

Реализация — несколько строк в `client/scripts/frontend-boundaries.mjs`:

<Source path="client/scripts/frontend-boundaries.mjs" from="const checkFsd = (file, target, typeOnly)" mark={["rule: 'fsd-layer'", "rule: 'fsd-slice'", "rule: 'fsd-public-api'"]} />

Скрипт разбирает все файлы компилятором TypeScript, вычисляет для каждого импорта слой и слайс источника и цели и применяет правила.

## Public API: index.ts

Каждый слайс экспортирует наружу только то, что объявлено в его `index.ts`. Остальные файлы — приватные:

<Source path="client/src/entities/catalog/index.ts" />

```ts
// ✅ через публичный API
import { useCatalogStore } from '@/entities/catalog'

// ❌ в обход: завязка на внутреннюю структуру слайса
import { useCatalogStore } from '@/entities/catalog/model/catalogStore'
```

Зачем это нужно: автор слайса может свободно переименовать и перенести внутренние файлы — пока `index.ts` экспортирует то же самое, потребители не ломаются. Это **инкапсуляция** на уровне папки.

Технически `index.ts` — обычный ES-модуль, который только **реэкспортирует** чужие экспорты:

<Doka from="js/modules" section="Модули в JavaScript">

В ES-модулях для экспорта используется ключевое слово `export`, а для импорта — `import`. […]

Если вдруг хотим изменить имя той функции или переменной, которую импортируем, мы можем использовать ключевое слово `as`. […] Экспортировать функциональность можно также уже и после того, как она определена. Это иногда бывает полезно, если хотим описать все экспорты в конце файла. Кроме того, это же помогает изменять названия при экспорте.

</Doka>

`export { useCatalogStore } from './model/catalogStore'` — это сокращение для «импортировать и тут же экспортировать». А `export type { CatalogItem } from './model/types'` экспортирует **только тип**: при сборке такая строка исчезает целиком и не создаёт зависимости во время выполнения. Это пригодится в следующем разделе.

## Исключение: @x для связей между сущностями

Иногда сущности нужен **тип** другой сущности: выполнению — тип позиции каталога. Запрет `fsd-slice` здесь слишком строг. FSD предлагает механизм `@x` («cross-import»): слайс-поставщик заводит отдельный адресный файл для конкретного потребителя:

<Source path="client/src/entities/catalog/@x/execution.ts" />

Файл `entities/catalog/@x/execution.ts` читается как «то, что catalog отдаёт execution». Правила проекта разрешают такой импорт **только type-only** (`import type`) — никаких runtime-зависимостей между сущностями.

## Legacy и миграция без поломок

Как перевести на FSD живой проект, не останавливая разработку? В Альфастрой временные связи «новый слой → legacy-код» перечислялись **точными парами файлов с причиной** в `client/fsd-migration-edges.json`. Линтер падал на любой новой связи и на любой **устаревшей** записи — список мог только уменьшаться. Сейчас он выглядит так:

<Source path="client/fsd-migration-edges.json" />

Пустой массив: все переходные связи мигрированы.

<Callout kind="rule" title="Правило миграции">
«Существующие legacy edges мигрировать явно, не ослабляя guard». Нельзя выключить правило «пока что» — можно только явно записать исключение, которое потом обязательно закроют.
</Callout>

<Callout kind="key">

- Три правила: **`fsd-layer`** (только вниз), **`fsd-slice`** (не к соседу по слою), **`fsd-public-api`** (только через `index.ts`).
- Правила проверяет **линтер** `lint:architecture` в CI: нарушить их незаметно нельзя.
- `@x` — адресный выход для **type-only** связей между сущностями; runtime-зависимостей между сущностями нет.
- Переходные исключения — точные пары файлов в `fsd-migration-edges.json`, список может только уменьшаться (сейчас он пуст).

</Callout>
