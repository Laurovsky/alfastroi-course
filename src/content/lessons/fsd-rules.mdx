Слои и слайсы бесполезны, если правила импорта можно нарушить незаметно. В Альфастрой они проверяются автоматически в CI скриптом `npm run lint:architecture`.

## Три правила

1. **`fsd-layer`** — нельзя импортировать слой выше своего.
2. **`fsd-slice`** — нельзя импортировать соседний слайс того же слоя.
3. **`fsd-public-api`** — в чужой слайс можно войти только через его `index.ts`.

Реализация — несколько строк в `client/scripts/frontend-boundaries.mjs`:

<Source path="client/scripts/frontend-boundaries.mjs" from="const checkFsd = (file, target, typeOnly)" mark={["rule: 'fsd-layer'", "rule: 'fsd-slice'", "rule: 'fsd-public-api'"]} />

Скрипт разбирает все файлы компилятором TypeScript, вычисляет для каждого импорта слой и слайс источника и цели и применяет правила.

## Public API: index.ts

Каждый слайс экспортирует наружу только то, что объявлено в его `index.ts`. Остальные файлы — приватные:

<Source path="client/src/entities/catalog/index.ts" />

```ts
// ✅ через публичный API
import { useCatalogStore } from '@/entities/catalog'

// ❌ в обход: завязка на внутреннюю структуру слайса
import { useCatalogStore } from '@/entities/catalog/model/catalogStore'
```

Зачем это нужно: автор слайса может свободно переименовать и перенести внутренние файлы — пока `index.ts` экспортирует то же самое, потребители не ломаются. Это **инкапсуляция** на уровне папки.

## Исключение: @x для связей между сущностями

Иногда сущности нужен **тип** другой сущности: выполнению — тип позиции каталога. Запрет `fsd-slice` здесь слишком строг. FSD предлагает механизм `@x` («cross-import»): слайс-поставщик заводит отдельный адресный файл для конкретного потребителя:

<Source path="client/src/entities/catalog/@x/execution.ts" />

Файл `entities/catalog/@x/execution.ts` читается как «то, что catalog отдаёт execution». Правила проекта разрешают такой импорт **только type-only** (`import type`) — никаких runtime-зависимостей между сущностями.

## Legacy и миграция без поломок

Как перевести на FSD живой проект, не останавливая разработку? В Альфастрой временные связи «новый слой → legacy-код» перечислялись **точными парами файлов с причиной** в `client/fsd-migration-edges.json`. Линтер падал на любой новой связи и на любой **устаревшей** записи — список мог только уменьшаться. Сейчас он выглядит так:

<Source path="client/fsd-migration-edges.json" />

Пустой массив: все переходные связи мигрированы.

<Callout kind="rule" title="Правило миграции">
«Существующие legacy edges мигрировать явно, не ослабляя guard». Нельзя выключить правило «пока что» — можно только явно записать исключение, которое потом обязательно закроют.
</Callout>
