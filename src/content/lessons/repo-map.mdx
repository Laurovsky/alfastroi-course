Альфастрой — **монорепозиторий**: клиент, сервер и общие типы лежат в одном git-репозитории и связаны через npm workspaces. Это значит: один `npm ci` в корне ставит зависимости всем частям, а изменение контракта API видно и серверу, и клиенту в одном коммите.

## Верхний уровень

```text
alfastroi/
├── client/            React-приложение (Vite, Zustand, Gravity UI)
├── server/            API на Express + TypeScript
├── packages/types/    @alfastroi/types — общие DTO клиента и сервера
├── sql/               история миграций 001…101 (полные тела функций)
├── supabase/          новые managed-миграции + production baseline
├── e2e/               сквозные тесты Playwright
├── docs/              архитектура, спеки, постмортемы
├── infra/             скрипты деплоя
├── .github/workflows/ CI, деплой, ночной бэкап
└── CLAUDE.md          контекст проекта: правила §§1–14 и грабли
```

Корневой `package.json` объявляет три workspace:

```json
{
  "workspaces": ["client", "server", "packages/types"]
}
```

Команды адресуются конкретному пакету флагом `-w`: `npm test -w server`, `npm run build -w client`.

### Что такое npm и зачем package-lock.json

<Doka from="tools/package-managers" section="Кратко">

Кусочки кода, которые можно использовать в своём приложении, называют _библиотеками_ или _пакетами_. Для удобной работы с ними существуют пакетные менеджеры (менеджеры зависимостей). Они помогают выбрать версию библиотеки и гарантируют безопасность.

[…] npm хранит список установленных пакетов в файле `package.json` в корне проекта.

</Doka>

<Doka from="tools/package-managers" section="Лок-файл">

[…] при установке и обновлении пакетов создаётся дерево зависимостей. Пакетный менеджер записывает его в специальный файл — лок-файл (от английского __lock__ — зафиксировать). В этом файле содержатся абсолютно все установленные в проекте зависимости с их точными версиями. По этому файлу пакетный менеджер установит точь-в-точь те же пакеты, которые были на момент генерации лок-файла.

☝️ Обязательно фиксируйте лок-файлы в системе контроля версий. Это поможет вам создавать воспроизводимые сборки приложения.

[…] Не рекомендуется использовать разные пакетные менеджеры в одном проекте — один пакетный менеджер может не понять другой лок-файл и установить другие версии библиотек, что может привести к ошибкам в вашем коде.

</Doka>

Отсюда разница двух команд, которые встречаются в проекте:

- `npm install` — ставит пакеты и **может обновить** `package-lock.json`. Используется, когда вы добавляете зависимость.
- `npm ci` — ставит **ровно** то, что записано в `package-lock.json`, и падает, если он расходится с `package.json`. Поэтому CI и деплой Альфастрой используют `npm ci`: в продакшен попадают те же версии, на которых прошли тесты.

В монорепозитории лок-файл **один на весь проект** (в корне). У клиента и сервера общие версии общих библиотек, а пакет `@alfastroi/types` не скачивается из интернета — npm связывает его с папкой `packages/types`.

Связывает слои **API** — договорённость о том, как одна программа говорит с другой:

<Doka from="tools/api" section="Кратко">

_API (Application Programming Interface)_ — это набор фич, которые одна программа представляет всем остальным. Она как бы говорит: «Смотрите, со мной можно говорить вот так и вот так, можете меня спросить о том-то через эту часть, а попросить что-то сделать — через эту».

В случае c клиент-серверным общением […] API может выступать как набор ссылок, по которым клиент обращается на сервер:

- `POST /api/v1.0/users` — для создания пользователя;
- `GET /api/v1.0/users` — для получения списка пользователей.

[…] Представьте, что вы написали модуль `CreditCalculator`, который считает проценты по кредитам какого-нибудь банка. Чтобы воспользоваться этим модулем в других частях программы, вы экспортируете его функции наружу. Эти функции — это API этого модуля.

</Doka>

В Альфастрой есть оба вида API из цитаты:

- **HTTP API сервера**: `POST /api/analyses`, `PATCH /api/analyses/:id/name`, `GET /api/analyses/:id/allowed-actions`… Так клиент говорит с сервером.
- **API модуля**: `index.ts` слайса на клиенте и `service.ts` модуля на сервере. Так части одной программы говорят друг с другом.

Сервер работает на Node.js:

<Doka from="tools/nodejs" section="Кратко">

Node.js — это способ запускать JavaScript-код не только в браузере. […]

В среде Node.js у приложения нет доступа к стандартным браузерным API. Например, `document` и `window` недоступны, потому что код исполняется вне браузера.

</Doka>

Поэтому код из `packages/types` не должен трогать `window` или `document`: он выполняется и в браузере, и в Node.js.

- **client** никогда не пишет в базу напрямую. Все изменения идут через API сервера.
- **server** — единственный «authority»: он проверяет права и статусы, вызывает функции Postgres.
- **PostgreSQL** хранит данные и выполняет многошаговые операции внутри транзакций (RPC-функции).

<Callout kind="info">
Supabase — это PostgreSQL плюс готовые сервисы: аутентификация (JWT), хранилище файлов (Storage) и REST-обёртка над таблицами. Сервер использует ключ `service_role` (полный доступ), а браузер — только публичный ключ, ограниченный правилами RLS.
</Callout>

## Сервер: модуль = папка домена

```text
server/src/
├── index.ts            собирает роуты всех модулей
├── db/supabase.ts      клиент с service_role
├── middleware/         auth, idempotency, errorHandler, rateLimit, upload
├── lib/                versionCheck, rpcRunner, withTimeout, auditWriter, zodHttp
└── modules/
    ├── catalog/        справочник работ
    ├── rates/          наборы расценок
    ├── analyses/       анализы (+ parsers, merge, readModels, useCases)
    ├── completions/    выполнение
    ├── approvals/      согласование (ApprovalWorkflow)
    └── …
```

Внутри модуля — одинаковые файлы: `routes.ts` (HTTP), `validators.ts` (Zod-схемы), `service.ts` (логика), `queries.ts` (чтение из базы), `types.ts`. Модули общаются **только через service.ts** друг друга.

## Клиент: слои Feature-Sliced Design

```text
client/src/
├── app/       инициализация, роутер, провайдеры
├── pages/     страницы маршрутов
├── widgets/   крупные блоки экрана (analysis-editor, execution-editor)
├── features/  пользовательские действия (import-analysis-tkp, select-approvers)
├── entities/  бизнес-сущности (catalog, analysis, work-item)
├── shared/    инфраструктура без бизнес-знаний (api, lib, ui)
└── components/, store/, lib/   legacy — мигрируется постепенно
```

FSD — тема модуля 7. Пока запомните главное: зависимости идут только сверху вниз, от `app` к `shared`.

## Общий пакет типов

Клиент и сервер обмениваются JSON. Чтобы форма этого JSON не разъезжалась, общие DTO лежат в `packages/types` — чистый TypeScript без зависимостей:

<Source path="packages/types/src/formatDisplayName.ts" />

Эту функцию импортируют и сервер (подписи в Excel-экспорте), и клиент (таблицы): `import { formatDisplayName } from '@alfastroi/types'`. Одна реализация — одно поведение.

## SQL и миграции

Схема базы меняется только миграциями — SQL-файлами, которые применяются по порядку. История `001…101` лежит в `sql/`, новые — в `supabase/migrations/` с префиксом-датой. Миграция — это не только таблицы: в ней живут функции (RPC), триггеры и права доступа.

<Callout kind="key">

- Монорепозиторий: `client`, `server` и `packages/types` в одном git-репозитории, связаны **npm workspaces**.
- Один `package-lock.json` фиксирует точные версии; CI ставит их через `npm ci`.
- Слои: браузер → API сервера → PostgreSQL. Браузер **не пишет** в базу напрямую.
- Общий для клиента и сервера код живёт в `@alfastroi/types` и не трогает `window` и `document`.

</Callout>
