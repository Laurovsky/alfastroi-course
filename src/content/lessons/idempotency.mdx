## Проблема: «я нажал один раз»

Прораб на объекте, связь — одна полоска. Он нажимает «Создать анализ». Запрос дошёл до сервера, анализ создан, но **ответ потерялся** в сети. Клиент видит таймаут и повторяет запрос. Итог — два одинаковых анализа.

Первое, что приходит в голову, — притормозить повторные нажатия. Для этого есть известный приём:

<Doka from="js/debounce" section="Кратко">

`debounce()` — это функция, которая «откладывает» вызов другой функции до того момента, когда с последнего вызова пройдёт определённое количество времени.

[…] Такую функцию используют, чтобы не бомбардировать сервер кучей запросов на каждый чих, а подождать, когда пользователь закончит или приостановит ввод, и только после этого отправить запрос на сервер.

</Doka>

`debounce` отлично решает **свою** задачу — схлопывает частые действия пользователя (ввод в поиске, двойной клик). Но в нашей истории пользователь нажал **один** раз. Запрос ушёл, сервер его выполнил, потерялся только ответ. Повтор делает не человек, а сетевой слой: ретрай `apiFetch` после таймаута, переотправка браузера, восстановление связи. На клиенте `debounce` не знает, выполнил ли сервер первый запрос. Это знает только сервер. Поэтому правило §9 и говорит: «Idempotency-Key header (не UI debounce)».

Вспомним, что Дока говорит о методах HTTP:

<Doka from="tools/http-protocol" section="Стартовая строка">

- `GET` — используется для получения данных от сервера.
- `POST` — используется для отправки данных на сервер.
- `PATCH` — то же, что и `PUT`, но используется для обновления части данных.
- `DELETE` — используется для удаления данных на сервере.

</Doka>

**Идемпотентная операция** даёт тот же результат, сколько раз её ни повтори. `GET` только читает — повторяй сколько угодно, данные не изменятся. `POST` «отправляет данные на сервер», и каждый `POST` создаёт **новый** анализ. Поэтому `POST` делают идемпотентным искусственно.

## Решение: Idempotency-Key

Клиент генерирует уникальный ключ **на одну логическую операцию** и отправляет его в заголовке. Повтор идёт с тем же ключом:

<Source path="client/src/shared/api/api.ts" from="export function withAutomaticIdempotencyKey" />

Сервер запоминает ключ и ответ. Повторный запрос с тем же ключом получает **сохранённый ответ**, а операция не выполняется второй раз.

## Состояния резервации

<Source path="server/src/middleware/idempotency.ts" from="type Reservation" to="}" />

| Состояние | Что значит | Ответ сервера |
|-----------|------------|---------------|
| `reserved` | Ключ новый — выполняем запрос | обычный ответ, который тоже сохраняется |
| `in_progress` | Первый запрос ещё выполняется | 409 «ещё выполняется» |
| `completed` | Ответ уже есть | тот же статус и тело из кэша |
| `endpoint_mismatch` | Ключ использован на другом адресе | 422 — ошибка клиента |
| `body_mismatch` | Ключ тот же, тело другое | 422 — ключ переиспользован неправильно |

Самое интересное — как middleware **перехватывает ответ**, чтобы сохранить его до отправки клиенту:

<Source path="server/src/middleware/idempotency.ts" from="const finalize = (body: unknown" mark={['complete(rawKey', 'then(deliver)']} />

Ответ сначала записывается в базу (`complete_idempotency_key`), и только потом байты уходят клиенту. Если сохранить не удалось — клиент получит 503 и честно повторит, а не будет думать, что всё прошло.

<Callout kind="info">
Резервация делается в Postgres-функции атомарно. Два одновременных запроса с одним ключом не могут оба получить `reserved`: так решается гонка, которую не решить проверкой «есть ли ключ?» + вставкой в два шага. Записи живут 24 часа (ошибки 5xx — 5 минут, чтобы можно было повторить).
</Callout>

## Подключение к роуту

```ts
router.post('/api/foo', authMiddleware, requireRole('x'), requireIdempotency('/api/foo'), handler)
```

<Callout kind="rule" title="Правило проекта §9">
Любой новый POST write-пути обязан получить idempotency. В проекте даже есть тест `idempotencyCoverage.test.ts`, который проверяет, что ни один POST-роут не забыт.
</Callout>

<Callout kind="key">

- **Идемпотентность** — повтор операции не меняет результат. `GET` идемпотентен сам, `POST` — нет.
- `debounce` схлопывает нажатия пользователя, но не спасает от **сетевого** повтора: только сервер знает, выполнялась ли операция.
- Ключ генерируется **один раз на логическую операцию**; повтор идёт с тем же ключом и получает сохранённый ответ.
- Резервация ключа атомарна (функция в Postgres), а ответ сохраняется **до** отправки клиенту.

</Callout>
