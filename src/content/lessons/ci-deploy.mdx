Код не готов, пока он не проверен и не доставлен. В Альфастрой путь от коммита до пользователя полностью автоматизирован — и почти каждый шаг появился после какого-то инцидента.

<Doka from="tools/ci-cd" section="Кратко">

Аббревиатура CI/CD означает «Continuous Integration/Continuous Delivery» — то есть «непрерывная интеграция/непрерывная доставка». Это подход к разработке, при котором задачи сборки, публикации, тестирования продукта полностью или частично автоматизированы. […] практики CI/CD прекрасно могут быть внедрены и в проекты, в которых участвует только один разработчик.

</Doka>

<Doka from="tools/ci-cd" section="Основные принципы">

Применение автоматизации процессов разработки снижает риск ошибок, позволяет оперативно чинить то, что не работает. Настройка инструментов CI/CD затрагивает и такую часть разработки, как создание единого окружения, в котором ведётся разработка программного продукта. […]

Например, использование одних и тех же npm-пакетов, их версий и инструментов тестирования позволяет разрабатывать приложение по единым стандартам качества. Случайные ошибки из-за неправильного окружения или другой операционной системы практически исключены.

</Doka>

«Единое окружение» в Альфастрой — это три вещи: Node.js 24 во всех задачах, `npm ci` по лок-файлу и PostgreSQL **17** в Docker для интеграционных тестов — той же версии, что в продакшене. Тест, который прошёл в CI, проверялся на тех же версиях, на которых работает пользователь.

## CI: что проверяется на каждом pull request

`.github/workflows/ci.yml` запускает три независимые задачи параллельно:

Клиентская задача — самая длинная. Посмотрите, сколько разных проверок проходит каждый PR:

<Source path=".github/workflows/ci.yml" from="- run: npm run format:check -w client" to="- run: npm run test:execution-editor -w client" />

| Шаг | Что ловит |
|-----|-----------|
| `format:check` | Prettier: единый формат, нет шумных диффов |
| `lint:styles` | Stylelint: ошибки CSS |
| `lint` | ESLint: ошибки TypeScript/React (правило проекта — 0 ошибок) |
| `lint:gravity` | Используются компоненты Gravity UI, а не самодельные кнопки |
| `lint:architecture` | Границы FSD (модуль 7) |
| `npm test` | Unit-тесты |
| `test:analysis-editor` и др. | Браузерные сценарии экранов в Playwright |
| `build` | Приложение собирается |

<Callout kind="tip" title="vitest не проверяет типы">
В конфиге CI есть комментарий: «vitest не тайпчекает — tsc отдельным шагом». Vitest выполняет TypeScript, просто отбрасывая типы, поэтому тест может пройти на коде с ошибкой типов. Отдельный `tsc --noEmit` закрывает эту дыру.
</Callout>

### Как устроен workflow

Все эти проверки описаны в YAML-файле, который выполняет GitHub Actions:

<Doka from="tools/github-actions" section="Как понять">

GitHub Actions — это инструмент для автоматизации рутины в области разработки программного обеспечения, автоматического тестирования, сборки и публикации приложений, который глубоко интегрирован в экосистему инструментов GitHub.

[…]

```yaml
name: EditorConfig

on:
  push

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - uses: actions/setup-node@v2
        with:
          node-version: '14'
      - run: npm ci
      - run: npm run editorconfig
```

Файл можно назвать произвольно, указать расширение _.yml_ и поместить в папку _.github/workflows_. Экшен автоматически запустится и выдаст результаты проверки на отдельной вкладке «Actions».

</Doka>

Сравните с началом `ci.yml` Альфастрой — структура та же, только задач три и запускаются они на pull request в `main`:

<Source path=".github/workflows/ci.yml" from="name: CI" to="- run: npm test -w server" />

- `on: pull_request` — **когда** запускать;
- `jobs` — независимые задачи; по умолчанию они идут **параллельно** (у Альфастрой их три);
- `steps` — шаги задачи по порядку: `uses` подключает готовый экшен (`checkout` скачивает код, `setup-node` ставит Node.js), `run` выполняет команду;
- `concurrency` с `cancel-in-progress` — новый push в ту же ветку отменяет недоделанный прогон, чтобы не тратить время на устаревший код.

Этот курс, кстати, публикуется так же: `.github/workflows/pages.yml` в его репозитории делает `npm ci → typecheck → test → build → deploy`.

## Деплой из main

Push в `main` запускает `deploy-production.yml`:

1. **verify** — тот же CI целиком (`uses: ./.github/workflows/ci.yml`). Красный CI — деплоя нет.
2. **Миграции** — применяются новые managed-миграции из `supabase/migrations`, затем проверяется, что нужные RPC существуют.
3. **Сборка клиента** с production-переменными.
4. **Установка релиза** — архив копируется на сервер и устанавливается как неизменяемый (immutable) релиз; активный релиз переключается атомарно.
5. **Проверка** — публичный `version.json` должен содержать id нового билда. Зелёный коммит без успешного деплоя не считается развёрнутым.

<Callout kind="warning" title="Порядок миграции и кода">
Некоторые миграции ломают старый код (например, удаляют старую сигнатуру функции). В CLAUDE.md такие помечены: «применять в одном окне с деплоем бэкенда». Для обратимых изменений безопаснее схема «расширить → задеплоить код → сузить».
</Callout>

## Наблюдаемость

- **Sentry** — ошибки клиента и сервера (только ошибки, без PII: в событии только id пользователя). `release` = короткий SHA коммита, поэтому видно, в какой версии появилась ошибка.
- **buildGuard** — в бандл зашит `__BUILD_ID__`, рядом лежит `version.json`. Вкладка со старым билдом при возврате фокуса видит расхождение и перезагружается (с 10-минутной защитой от цикла). Это ответ на инциденты с «зомби-вкладками».
- **Ночной бэкап** — `pg_dump` схемы в 02:00 UTC в артефакт GitHub на 30 дней.

<Callout kind="key">

- **CI** проверяет каждый pull request: формат, линтеры (включая границы FSD), типы, unit-, db- и браузерные тесты, сборку.
- **CD**: push в `main` → тот же CI → миграции → сборка → неизменяемый релиз → проверка `version.json` снаружи.
- Единое окружение: одна версия Node.js, `npm ci` по лок-файлу, та же версия PostgreSQL, что в продакшене.
- После релиза — наблюдаемость: Sentry по ошибкам, buildGuard против устаревших вкладок, ночной бэкап.

</Callout>
