Справочник работ — это дерево из ~18 тысяч узлов: пакет → система → подсистема → раздел → работа. Как хранить дерево в реляционной базе и как его собирать — одна из первых архитектурных развилок проекта.

## Соблазн: код как структура

У каждой работы есть код: `6.2.3.1.4`. Он уже выглядит как путь в дереве — родитель `6.2.3.1`, дед `6.2.3`. Почему бы не строить дерево по нему?

Потому что код — **бизнес-идентификатор для людей**, а не структура:

- коды меняются (переименовали раздел — поменялись коды всех потомков);
- бывают нестандартные коды и дубли между пакетами;
- строковое сравнение кодов ломает порядок: `'6.10' < '6.2'`, потому что символ `1` меньше `2`.

<Callout kind="rule" title="Правило проекта §1">
Структура — `parent_id` (внешний ключ на родителя) + `sort_order` (порядок среди братьев). `level` — денормализованная глубина для удобства. **`code` используется только для отображения.**
</Callout>

```sql
work_catalog: id, package_id, code, parent_id (FK → work_catalog), sort_order, level, name, type, unit
```

`parent_id` даёт базе целостность (нельзя сослаться на несуществующего родителя) и позволяет обходить дерево рекурсивным запросом (`WITH RECURSIVE`). `sort_order` с шагом 10 позволяет вставить элемент между соседями без перенумерации всех.

## Сборка дерева из плоского списка

Сервер отдаёт каталог плоским массивом строк. Клиентский стор строит из него дерево за линейное время — через `Map` «родитель → дети»:

<Source path="client/src/entities/catalog/model/catalogStore.ts" from="function buildTree" />

Обратите внимание на три приёма:

1. **Один проход для группировки** — `Map<parent_id, item[]>` вместо поиска детей фильтром для каждого узла (это было бы O(n²) на 18 тысячах строк).
2. **Сортировка внутри группы** по `sort_order` — не по имени и не по коду.
3. **Рекурсия** `toNodes(parentId)` собирает узлы сверху вниз.

Разберём каждый приём по Доке.

### Приём 1. Map — словарь «ключ → значение»

<Doka from="js/map" section="Кратко">

`Map` — коллекция для хранения данных любого типа в виде пар `[ключ, значение]`, то есть каждое значение сохраняется по _уникальному_ ключу, который потом используется для доступа к этому значению. Причём в качестве ключей тоже принимаются значения любого типа.

Основные методы для работы с коллекцией `Map`:

- `set(ключ, значение)` — устанавливает значение;
- `get(ключ)` — возвращает значение;
- `has(ключ)` — проверяет наличие переданного ключа;
- `values()` — возвращает итератор всех значений коллекции;
[…]

</Doka>

<Doka from="js/map" section="Отличия от объектов">

Обычные объекты тоже подходят для хранения данных. Однако ключи в них могут быть только строками или символами […]

`Map` же позволяет использовать в качестве ключа любое значение: объект, функцию, примитивные значения и даже `null`, `undefined` и `NaN`.

</Doka>

Последняя фраза — ровно то, что нужно `buildTree`. У корневых узлов `parent_id === null`, и `childrenMap.get(null)` работает. В обычном объекте ключ `null` превратился бы в строку `"null"` — и совпал бы с узлом, у которого id случайно равен строке `"null"`. `Map` различает их честно.

А `.values()` используется во втором цикле: `for (const bucket of childrenMap.values())` перебирает все группы детей, чтобы отсортировать каждую.

### Приём 2. Почему один проход лучше фильтра

<Doka from="tools/algorithm-complexity" section="Кратко">

Вычислительная сложность алгоритма описывает, как выполняемый алгоритмом объём работы зависит от размера входных данных.

[…] _O_, читается как «О», «О-большое» или «биг (big) О», описывает оценку сложности сверху. То есть максимальное количество операций, которое алгоритм может выполнить в худшем случае. […] Например, O(n) означает, что сложность алгоритма растёт линейно. Это означает, что время выполнения алгоритма увеличивается прямо пропорционально размеру входных данных […]

Временная сложность этого кода — ϴ(n ^ 2). Он выполняет n операций для каждого элемента массива — n × n. Если массив состоит из десяти элементов, то код выполнится за 100 операций.

</Doka>

Применим к каталогу. Наивный вариант — для каждого узла искать детей через `items.filter(i => i.parent_id === node.id)`: это n узлов × n проверок. При 18 600 строках — около **346 миллионов** сравнений, вкладка замрёт на секунды. Вариант с `Map`: один проход, чтобы разложить строки по корзинам, и мгновенный `get` для каждого узла — порядка **18 600** операций. Разница в двадцать тысяч раз.

### Приём 3. Рекурсия: функция, которая вызывает сама себя

<Doka from="js/recursion" section="Деревья">

_Дерево_ — это структура, в которой у каждого узла может быть несколько дочерних подузлов — «детей».

[…] У каждого дерева есть корень — узел, из которого берут начало остальные узлы.

Работать с деревьями с помощью циклов (итеративно) неудобно. Представьте, что мы хотим получить названия всех элементов на странице. Да, мы можем пройтись циклом по 1-му уровню или 2-му, но дальше нужно думать, как определять, где мы были, где ещё нет и куда идти дальше.

С рекурсией обход дерева становится немного проще.

</Doka>

<Doka from="js/recursion" section="Базовый случай">

_Базовый случай_ — это условие, при выполнении которого рекурсия заканчивается и функция больше не вызывает саму себя.

[…] Без базового случая любая рекурсивная функция уйдёт в бесконечное выполнение, потому что будет вызывать себя без конца.

В JS это приводит к переполнению стека вызовов, и функция останавливается с ошибкой.

</Doka>

Где базовый случай в `toNodes`? Он неявный: у листа нет детей, `childrenMap.get(item.id)` возвращает `undefined`, срабатывает `?? []`, и `map` по пустому массиву не делает ни одного рекурсивного вызова. Рекурсия останавливается сама.

<Callout kind="danger" title="Грабли: циклы в parent_id">
А теперь представьте, что данные испорчены: узел A ссылается на B, а B на A. У такой пары **никогда** не наступит базовый случай — дети есть всегда. Рекурсия уйдёт в бесконечность, и вкладка повиснет (или упадёт с переполнением стека). Правило §13: любой обход графа на клиенте — **с `visited` Set**. Заодно это защищает от дублей React-ключей.
</Callout>

<Doka from="js/set" section="Кратко">

`Set` (по-русски говорят _множество_) — коллекция для хранения уникальных значений любого типа. Одно и то же значение нельзя добавить в `Set` больше одного раза.

[…] Основные методы для работы с коллекцией:

- `add()` — добавить элемент.
- `delete()` — удалить элемент.
- `has()` — проверить, есть ли элемент в коллекции.

</Doka>

`visited.has(id)` отвечает на вопрос «я здесь уже был?» за одну операцию, независимо от размера дерева. Перед заходом в узел проверяем `has`, затем делаем `add` — и второй заход в тот же узел становится невозможен.

<Callout kind="key">

- Структура дерева — `parent_id` + `sort_order`; `code` только для людей.
- Коды сравниваются **по сегментам как числа**, иначе `'6.10' < '6.2'`.
- Плоский список → дерево: **один проход в `Map`** (O(n)) вместо фильтра для каждого узла (O(n²)).
- Рекурсия нуждается в **базовом случае**; при испорченных данных его может не быть — поэтому **`visited` Set**.

</Callout>
