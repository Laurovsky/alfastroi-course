## Проблема потерянного обновления

Два инженера одновременно открыли один анализ. Оба видят цену 1000 ₽. Первый ставит 1500 и сохраняет. Второй, не обновив страницу, ставит 1800 и сохраняет. Правка первого **молча исчезла** — никто даже не узнал, что она была.

Это классическая проблема **lost update**. Попробуйте сами: сначала с выключенной проверкой, потом с включённой.

## Пессимистичная и оптимистичная блокировка

- **Пессимистичная**: «я редактирую — остальные ждут». Нужны блокировки, таймауты на случай закрытой вкладки, очередь. Для веб-интерфейса с долгими сессиями редактирования неудобна.
- **Оптимистичная**: «конфликты редки — проверим при записи». У строки есть счётчик `version`. Клиент запоминает версию при чтении и при записи говорит: «обнови, **только если** версия всё ещё та, что я видел».

```sql
UPDATE analysis_rates
   SET unit_rate = 1800, version = version + 1
 WHERE id = $1 AND version = $2   -- $2 = версия, которую видел клиент
```

Если кто-то успел записать раньше, `version` уже другая, и `WHERE` не найдёт строку: затронуто 0 строк → конфликт.

<Callout kind="rule" title="Правило проекта §2">
Горячие таблицы — `execution_analyses`, `work_items`, `analysis_rates`, `completions` — меняются **только** с проверкой версии. `data == null` → `ConflictError` (409) → сообщение пользователю и перезагрузка. **Никакой тихой перезаписи.**
</Callout>

Почему это работает без гонок: проверка и запись — **одна** SQL-команда. База гарантирует атомарность UPDATE, поэтому между «проверил версию» и «записал» никто не вклинится. А вот так делать нельзя:

```ts
// ❌ гонка: между SELECT и UPDATE другой запрос может записать свою версию
const row = await select(id)
if (row.version !== prevVersion) throw new ConflictError()
await update(id, patch)
```

## Конфликт — это отдельный класс ошибки

Обратите внимание: `conditionalUpdate` бросает не просто `Error`, а `ConflictError`. Вот как объявлен этот класс:

<Source path="server/src/lib/versionCheck.ts" from="export class ConflictError" />

Это стандартный приём JavaScript, который Дока описывает так:

<Doka from="js/errors" section="Собственный класс ошибок">

Можно расширять базовый класс `Error` и создавать собственные типы ошибок.

```js
class WrongDataTypeForSumError extends Error {
  constructor(message) {
    super(message)
    this.name = 'WrongDataTypeForSumError'
  }
}
```

</Doka>

Структура один в один: `extends Error`, вызов `super(message)`, своё `name`. Зачем отдельный класс, если можно `throw new Error('конфликт')`? Чтобы код выше по стеку мог **различать** ошибки без разбора текста: `errorHandler` проверяет `err instanceof ConflictError` и отвечает 409, а любую другую ошибку считает 500. Текст сообщения можно перевести или переформулировать — класс останется тем же.

Ещё одна деталь `ConflictError` — значение по умолчанию: `message = 'Запись была изменена другим пользователем'`. Поэтому `new ConflictError()` без аргументов уже несёт понятный пользователю текст.

## Что видит пользователь

Клиент получает 409 и показывает `ConflictDialog`: «Запись была изменена другим пользователем». Пользователь перезагружает данные, видит чужую правку и решает, что делать. Это честнее, чем «последний победил».

## Копия, а не ссылка

В упражнении ниже есть требование «возвращать копию строки, а не ссылку из хранилища». Вот почему это важно:

<Doka from="js/shallow-or-deep-clone" section="Кратко">

При копировании объекта, его примитивные свойства (числа, строки, булевы значения) дублируются, а вложенные объекты (nested properties) остаются общими с оригиналом в виде ссылок. Этот тип копирования называется _поверхностным_ (shallow). […]

Если необходимо полностью скопировать сложную структуру данных, например, массив объектов, то нужно делать _глубокое_ (deep) или полное копирование данных.

</Doka>

Если `get(id)` вернёт ссылку на объект внутри хранилища, вызывающий код сможет написать `row.unit_rate = 0` и **изменить «базу» в обход** `conditionalUpdate` — без проверки версии и без увеличения `version`. Поверхностная копия `{ ...row }` защищает от этого, потому что у строки нет вложенных объектов, только примитивы. В настоящей базе этой проблемы нет: Supabase каждый раз возвращает новый JSON.

<Callout kind="key">

- **Lost update** — вторая запись молча затирает первую. Защита — поле `version`.
- `UPDATE … WHERE id = ? AND version = ?` — проверка и запись **одной командой**, поэтому гонки нет. «Сначала SELECT, потом UPDATE» — гонка.
- 0 затронутых строк → `ConflictError` → HTTP 409 → пользователь перезагружает данные. Автоповтор с новой версией запрещён.
- Свои классы ошибок (`extends Error`) позволяют различать ошибки через `instanceof`, а не по тексту.

</Callout>
