Альфастрой — в основном функциональный код. Но архитектурные правила явно выделяют места для классов: парсер смет `TKPParser`, машина согласования `ApprovalWorkflow` и (пока в планах) экспортёр документов `DocumentExporter`. Разберёмся, почему именно там.

Сначала — зачем вообще ООП:

<Doka from="tools/oop" section="Кратко">

Хороший код адекватно отражает систему, которую описывает, он устойчив к изменениям в этой системе. Плохой код запутанный, хрупкий и непонятный — он замедляет разработку.

Код становится плохим, когда он перестаёт соответствовать реальности — бизнес-логике, правилам поведения частей системы, их отношениям друг с другом. Бизнес-логика — это территория. Код — карта этой территории. Чем точнее карта, тем проще справляться с изменениями в требованиях и даже предвидеть их.

Объектно-ориентированное программирование — одна из парадигм, которые помогают спроектировать программу так, чтобы она верно отражала эти правила и была устойчивой к изменениям.

</Doka>

Ключевое слово — «устойчивой к изменениям». В Альфастрой классы стоят именно там, где изменения **предсказуемы**: форматов смет будет больше (PDF уже в планах), типов сущностей на согласовании — тоже. Там, где ничего такого не ожидается, проект обходится функциями.

## Задача: разные форматы смет

Сметы приходят в разных форматах: выгрузка 1С (ПИК), шаблон Sminex, в будущем PDF. Форматы различаются **разбором файла**, но дальше обработка общая: построить иерархию строк, найти системы, определить тип строки.

## Абстрактный класс

<Source path="server/src/modules/analyses/constructor/parsers/TKPParser.ts" from="export abstract class TKPParser" to="abstract parse(" />

- `abstract class` нельзя создать напрямую (`new TKPParser()` — ошибка компиляции).
- `abstract parse(...)` — метод **без реализации**: каждый формат обязан его написать.
- `protected` методы (`buildHierarchy`, `detectSystems`, `detectRowType`) — общая логика, доступная наследникам, но не внешнему коду.

<Source path="server/src/modules/analyses/constructor/parsers/TKPParser.ts" from="protected buildHierarchy" />

Наследники — `Xlsx1cTKPParser` (выгрузка 1С) и `SminexXlsxParser` — реализуют `parse` по-своему, а `buildHierarchy` и `detectSystems` получают бесплатно. В тесте `TKPParser.test.ts` есть даже минимальный `class TestParser extends TKPParser` — так тестируют общую логику абстрактного класса.

## Полиморфизм

Код, который вызывает парсер, не знает, какой именно формат перед ним:

```ts
async function importEstimate(parser: TKPParser, file: Buffer) {
  const rows = await parser.parse(file) // какой именно формат — не важно
  // ... дальше общий пайплайн
}
```

Это и есть полиморфизм:

<Doka from="tools/oop" section="Полиморфизм">

Полиморфизм — возможность использовать объект, не зная какой это конкретно объект, а лишь опираясь на некоторые заранее определённые абстрактные признаки.

[…] Интерфейс — это такой «контракт на поведение». Он говорит, как именно должен себя вести любой объект, который его реализует.

[…] Код, написанный и заточенный под одну конкретную сущность, как правило, высоко сцеплен.

[…] высокое сцепление — это когда модули слишком много знают друг о друге. Это плохо, потому что при высоком сцеплении изменение в одной части программы будет вызывать много изменений в других частях. Полиморфизм помогает уменьшить сцепление кода.

**Плюсы**

1. _Меньше `if-else` веток_, потому что нам реже нужно знать, какой именно перед нами объект, чтобы сделать над ним какое-то действие.
2. _При изменении системы нужно менять меньше кода_, это напрямую вытекает из первого пункта — то есть уменьшается сцепление.

</Doka>

«Абстрактный признак» для парсера — метод `parse(file): Promise<RawRow[]>`. Без полиморфизма пайплайн импорта выглядел бы как `if (format === '1c') {…} else if (format === 'sminex') {…}`, и каждый новый формат требовал бы правки этого `if` во всех местах, где он повторяется.

Дока отмечает, что в чистом JavaScript нет интерфейсов, и полиморфизм приходится обеспечивать «отчасти костыльным способом». В Альфастрой эту проблему снимает TypeScript: `abstract class` и `interface` — полноценные контракты, которые проверяет компилятор.

## Принцип Open/Closed

**Открыт для расширения, закрыт для изменения.** Новый формат сметы (PDF) — это **новый класс** `PdfTKPParser extends TKPParser`. Существующие парсеры и код, который их вызывает, не меняются.

<Doka from="tools/oop" section="Принцип открытости и закрытости (OCP) — O">

Принцип открытости и закрытости (Open-Closed Principle) — решает проблему, когда вносить изменения в проект слишком сложно, долго или дорого.

Модули, которые удовлетворяют этому принципу:

- _открыты для расширения_ — их функциональность может быть дополнена с помощью других модулей, если изменятся требования;
- _закрыты для изменения_ — их код менять нельзя (можно лишь исправлять ошибки).

</Doka>

В правилах Альфастрой это записано одной строкой: «Open/Closed (новый формат = новый парсер-класс)». Цена принципа — `TKPParser` должен быть спроектирован так, чтобы новому формату хватило переопределить `parse`. Если бы PDF потребовал другой логики иерархии, пришлось бы менять базовый класс — и принцип нарушился бы.

### Это ещё и паттерн «Стратегия»

<Doka from="tools/design-patterns-behaviorial" section="Стратегия">

Стратегия (англ. _strategy_) позволяет выбирать и даже менять алгоритм работы в зависимости от ситуации.

Допустим, мы пишем приложение-навигатор. Когда оно будет прокладывать путь между точками, ему надо будет знать, для кого этот путь: пешехода, велосипедиста, автомобилиста. В зависимости от ситуации мы будем использовать разные алгоритмы и маршруты на карте.

Для использования стратегии мы объявляем интерфейс, который описывает алгоритмы, из которых мы будем выбирать:

```ts
interface RouteStrategy {
  findRoute(from: Point, to: Point): Instruction[];
}
```

</Doka>

Подставьте вместо маршрутов форматы смет: «интерфейс алгоритма» — это `parse(file)`, конкретные стратегии — `Xlsx1cTKPParser` и `SminexXlsxParser`, а выбор стратегии делается по пакету работ (`work_packages.estimate_parser: 'pik_1c' | 'sminex'` — это поле видно в `catalogStore` из урока про дерево).

<Callout kind="info" title="Абстрактный класс или интерфейс?">
**Интерфейс** — только контракт («у объекта есть метод parse»). **Абстрактный класс** — контракт плюс общая реализация. Здесь у форматов много общего кода, поэтому класс. Если бы общего кода не было, хватило бы `interface TKPParser { parse(...): Promise<RawRow[]> }` и функций.
</Callout>
