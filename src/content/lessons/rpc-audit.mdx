## Зачем бизнес-логика в базе

Отправка пакета выполнения на согласование — это несколько шагов: проверить статус, перевести completions в `pending_field_approval`, прикрепить черновики актов, вставить строки назначений согласующих, записать аудит. Если сервер упадёт после третьего шага, данные останутся **наполовину изменёнными**.

**Транзакция** решает это: либо все шаги, либо ни одного. В Альфастрой многошаговые операции пишутся как **PL/pgSQL-функции** (RPC), а сервер вызывает их одной командой `supabase.rpc('fn', params)`. Любая ошибка внутри функции — автоматический откат.

<Callout kind="rule" title="Правило проекта §4">
Multi-step — внутри Postgres-функции. Простые single-table UPDATE — напрямую с version-check (`conditionalUpdate`).
</Callout>

## Анатомия RPC-функции

Разберём `rename_analysis` целиком:

<Source path="sql/101_rename_analysis.sql" mark={['SECURITY DEFINER', 'FOR UPDATE', "'CONFLICT:", "'FORBIDDEN:", 'INSERT INTO audit_log', 'REVOKE']} />

Построчно:

1. `SECURITY DEFINER` — функция выполняется с правами владельца, а не вызывающего. Поэтому её вызов надо строго ограничить (последние строки — `REVOKE`/`GRANT`, урок 4.3).
2. `SET search_path = public` — защита от подмены таблиц через `search_path`.
3. **Проверка роли** — второй рубеж после `requireRole`.
4. **Валидация** — тоже повтор Zod-проверки: функцию могут вызвать не только из этого роута.
5. `SELECT … FOR UPDATE` с `version = p_prev_version` — блокировка строки и проверка версии. Если версия не совпала — `RAISE EXCEPTION 'CONFLICT: …'`.
6. **CTE** `before_state` → `updated` → `INSERT INTO audit_log`: снимок «до», обновление, запись аудита — одной командой.

## Соглашение об ошибках

Функция сообщает о бизнес-ошибке префиксом в тексте исключения. Сервер распознаёт префикс и превращает его в класс:

<Source path="server/src/lib/rpcRunner.ts" from="export async function runRawRpc" />

Путь ошибки получается такой: `RAISE EXCEPTION 'CONFLICT: …'` в Postgres → `runRawRpc` бросает `ConflictError` → ошибка всплывает через сервис и роут (там `catch (e) { next(e) }`) → `errorHandler` превращает её в 409. Ни сервис, ни роут не разбирают ошибку сами — они просто пропускают её наверх. Механизм «поймать там, где можно обработать» — это `try...catch`:

<Doka from="js/try-catch" section="Кратко">

Конструкция `try...catch` позволяет выполнить произвольный код, но если в нем произошла ошибка, то программа не остановит своё выполнение, а перейдёт в блок `catch`, где ошибку можно обработать.

[…] С пойманной в `catch` ошибкой можно поступить как угодно: отправить данные в специальный логгер, обработать данные из неё и даже выбросить новую ошибку, которая может быть поймана в другом месте и т.д.

</Doka>

Последняя фраза — ровно то, что делает `runRawRpc`: «ловит» ответ базы с ошибкой и **выбрасывает новую**, более осмысленную ошибку (`ConflictError` вместо сырого сообщения PostgREST), которая «поймана в другом месте» — в `errorHandler`.

## Audit log: история, которую нельзя переписать

`audit_log` — append-only таблица: в неё только добавляют.

```text
audit_log: entity_type, entity_id, action, before_state (JSONB), after_state (JSONB),
           changed_by, batch_id, source_action, created_at
```

- `action` строго `'create' | 'update' | 'delete'` (CHECK). Смысл действия — в `source_action` (`analysis_rename`, `rate_update`, …).
- `before_state`/`after_state` — полные JSON-снимки строки. Из них интерфейс показывает «было → стало» (`<s>1000</s> 1500`).
- `batch_id` группирует связанные изменения одной операции.

Снимки хранятся как **JSONB** — двоичная форма JSON в Postgres. `to_jsonb(ea.*)` превращает строку таблицы целиком в JSON-объект:

<Doka from="tools/json" section="Кратко">

JSON — самый популярный формат обмена данными между приложениями. Этот формат очень похож на объекты JavaScript. Объекты легко трансформируются в JSON для отправки на сервер.

[…] JSON определяет небольшой набор правил форматирования для представления основных типов данных и может применяться почти с любым языком программирования.

</Doka>

Почему JSON, а не отдельные колонки «старая цена», «новая цена»? Аудит пишут **разные** таблицы с разными полями (`analysis_rates`, `work_items`, `execution_analyses`…). Один JSON-столбец вмещает строку любой формы, а когда в таблицу добавят колонку, аудит подхватит её автоматически — схему `audit_log` менять не придётся. А на клиенте этот JSON сразу становится обычным JavaScript-объектом, и «было → стало» считается сравнением полей.

<Callout kind="rule" title="Audit-first (§3)">
Каждый новый write-путь обязан писать аудит **в той же транзакции**. Аудит, записанный отдельным запросом после основного, может потеряться при сбое — и история будет врать.
</Callout>

<Callout kind="key">

- Многошаговая операция живёт в **одной Postgres-функции** = одной транзакции: либо всё, либо ничего.
- Функция сама проверяет роль, данные и версию (`FOR UPDATE` + `version`), а заканчивается `REVOKE`/`GRANT`.
- Бизнес-ошибки — `RAISE EXCEPTION` с префиксом `CONFLICT:` / `FORBIDDEN:` → классы ошибок → 409 / 403.
- Аудит пишется **в той же транзакции**: JSONB-снимки «до» и «после», `action` ∈ create/update/delete, смысл — в `source_action`.

</Callout>
